# 레드오션 — C#/.NET 개발

## 적용 범위와 우선순위

- Windows의 **Microsoft Visual Studio 전용** C#/.NET 앱과 클래스 라이브러리의 설계, 구현, 수정, 검토에 적용한다. UI가 없는 라이브러리에도 적용한다. 코드 편집·빌드·디버깅의 기준 환경은 Visual Studio로 고정한다. UI가 필요한 프로젝트에서는 WinForms를 사용하고 사용자가 Visual Studio 디자이너에서 편집할 수 있도록 구현한다. Visual Studio Code, Rider 또는 다른 UI 프레임워크로 전환하지 않는다. Visual Studio를 직접 열지 않고 코드 편집과 사용 가능한 빌드 도구로 작업해도 된다. IDE나 디자이너 접근 제한만으로 구현을 차단하지 않으며, 수행하지 않은 검증은 보고한다.
- 독립적으로 사용하는 스킬이며 다른 스킬의 지침·역할 절차에 의존하지 않는다. 현재 작업의 사용자 지시, 대상 솔루션의 명시적 설정과 기존 패턴, 이 스킬의 기본 규칙 순으로 따른다. 충돌이 있으면 담당 에이전트가 사용자 지시를 우선하고 영향과 해결 방법을 기록한다.
- 시작할 때 `.sln`/`.csproj`, `TargetFramework`, `LangVersion`, `Nullable`, `.editorconfig`, `Directory.Build.*`, 분석기, NuGet 설정, 테스트·빌드 구성과 관련 구현을 확인한다. UI가 있으면 UI/디자이너 패턴도 확인한다. 기존 프로젝트의 문법, 이름, 들여쓰기, 공백, 중괄호, 파일 구성, 예외·이벤트 스타일을 따른다. 수정하지 않는 코드를 일괄 재서식하거나 개명하지 않는다.
- 새 프로젝트는 해당 시점에 정식 출시되고 지원되는 최신 .NET LTS를 기본 후보로 삼는다. WinForms 앱이면 Windows 대상 프레임워크와 `UseWindowsForms`를 설정한다. UI 없는 라이브러리에 WinForms 참조나 Windows 대상 프레임워크를 불필요하게 강제하지 않는다. 기존 프로젝트의 대상 프레임워크와 언어 버전은 작업 요구가 없으면 유지한다. .NET 12, 14 등 향후 LTS는 실제 출시·지원·도구 호환성을 확인한 뒤 사용한다. 버전 업그레이드, 프리뷰 기능, 새 패키지는 범위와 영향을 설명하고 필요한 승인을 받는다.
- XML 문서 주석(`///`)을 새로 쓰지 않는다. 필요한 설명은 일반 주석(`//`, `/* */`)으로 *왜* 그렇게 처리했는지 적는다. 기존 주석을 이유 없이 삭제하거나 변환하지 않는다.

## 작업 모드·역할·모델

- **기본값은 서브에이전트 사용이다.** 사용자가 `서브에이전트를 사용하지 마`라고 명시한 작업에서만 서브에이전트를 만들지 않고 단독으로 진행한다. 별도 지시가 없거나 `서브에이전트를 사용해`라고 하면 아래 다섯 역할을 각각 다른 에이전트에 배정한다. 사용자가 명시한 선택을 작업 중 임의로 뒤집지 않는다.
- 단독 작업에서는 한 에이전트가 범위 설정, 설계, 해당하는 경우 UI 검토, 구현, 자체 검증 및 최종 판단을 책임진다. QC가 독립적으로 수행되었다고 주장하지 않는다. 필요한 사용자 결정이나 Visual Studio 접근 제한은 그대로 보고한다.
- 다중 에이전트 작업에서는 다섯 역할 모두 신규 에이전트를 시작할 때 **GPT-6.1 Sol** (`gpt-6.1-sol`)과 **Medium** (`medium`) 추론 수준을 지정한다. 이미 실행 중인 에이전트의 모델이 바뀐 것처럼 주장하지 않는다. 지정 모델이나 슬롯이 제공되지 않으면 조용히 대체하거나 다섯 명이 참여했다고 보고하지 말고 제약을 사용자에게 알린다.

| 역할 | 모델 | 책임 |
| --- | --- | --- |
| 프로젝트 매니저(PM) | GPT-6.1 Sol Medium | 요청·완료 기준·범위·우선순위, 작업 배정과 충돌 해결, 최종 검수 및 종료 결정 |
| 시스템 설계자 | GPT-6.1 Sol Medium | 기존 구조와 재사용 후보 조사, 인터페이스·변경 영향·작업 경계·검증 계획, 개발 지시의 구체화 |
| GUI 디자이너 | GPT-6.1 Sol Medium | UI 작업 시 WinForms 화면·디자이너·옵션·이벤트 검토. UI 없는 라이브러리에서는 GUI 산출물을 만들지 않고 공개 API 사용성을 검토하며 UI 항목은 해당 없음으로 기록 |
| 소프트웨어 개발자 | GPT-6.1 Sol Medium | 기존 코드 재사용 중심 구현, 빌드·실행 검증, 근거와 차단 요소 보고 |
| 프로그램 검토 및 검증 QC | GPT-6.1 Sol Medium | 변경 사항과 완료 기준의 독립 검토, 재현 가능한 결함·미검증 범위 보고, 수정 후 재검증 |

다중 에이전트 모드에서는 다음 순서로 진행한다.

1. PM이 작업 목표·완료 기준을 정하고, 시스템 설계자가 영향 범위와 재사용 경로, 담당 파일·인터페이스·검증 방법을 정리한다. PM과 시스템 설계자는 구현 담당자가 추가 추측 없이 수행할 수 있도록 입력 파일, 요구 동작, 경계 조건, 완료 증거를 명시한다.
2. 역할 간 필요한 결정은 짧은 작업 기록으로 공유한다. UI 작업이면 GUI 디자이너와 개발자가 디자이너 관리 영역과 런타임 로직의 계약에 합의한다. UI가 없으면 디자이너 단계를 건너뛴다. 공유 파일 편집과 선행 설계 결정은 순차 처리한다.
3. 실제로 독립적이고 시간이 의미 있게 드는 조사·구현·검증은 사용 가능한 슬롯과 PC의 CPU·메모리·빌드 환경을 고려하여 병렬 처리한다. 같은 파일의 동시 편집이나 의존 작업의 무리한 병렬화는 피한다. PM은 결과를 통합하고 누락된 검증을 배정한다.
4. QC는 합격 여부와 근거를 PM에게 전달한다. QC가 문제를 제기하면 PM이 재현·영향을 확인하고 시스템 설계자와 수정 방향을 정한 후 담당자에게 재작업을 배정한다. QC가 수정 결과를 재검증한다. QC 통과 후에도 PM이 원래 완료 기준으로 최종 검수하고 종료 여부를 결정한다.

## 구현과 의존성

- 요구를 만족하는 가장 작은 변경을 선택한다. 기존 프로젝트 코드·도우미·SDK 래퍼와 해당되는 경우 기존 UI 컨트롤을 먼저 조사하고, 그다음 .NET 표준 라이브러리와 필요한 플랫폼 기본 기능을 검토한다. 불필요한 기능·계층·인터페이스·패키지는 만들지 않는다.
- 외부 패키지가 필요해 보이면 추가 전에 필요한 기능, 프로젝트 내 대안, 표준·플랫폼 대안, 후보와 버전, 라이선스·의존성·배포·유지보수 영향을 사용자에게 제시하고 처리 방향에 대한 승인을 받는다. 다중 에이전트 작업에서는 PM이 이를 조율한다. 승인 전 설치하거나 프로젝트에 추가하지 않는다.
- 대상 프레임워크와 C# 버전에서 실제 제공되는 API만 사용한다. 기존 공개 API, 직렬화 형식, 네이티브 ABI와 호환성에 영향을 주는 변경은 먼저 영향 범위를 설명한다. `nullable`이 활성화되어 있으면 null 허용 계약을 타입에 반영하고 경고 원인을 해결한다. `!`나 경고 억제는 증명 가능한 국소 예외에만 쓰고 이유를 일반 주석으로 적는다.
- 소유한 `IDisposable`/`IAsyncDisposable` 객체, 이벤트 구독, 타이머, 스트림, 카메라·네이티브 핸들의 해제 시점을 명확히 한다. 공유받은 객체를 소유 계약 없이 해제하지 않는다. 외부 입력·SDK 반환값은 경계에서 검증하고 빈 `catch`나 예외 은폐를 하지 않는다. 사용자 메시지와 진단 로그는 기존 프로젝트 방식으로 구분한다.
- 비동기 API가 필요한 라이브러리 작업에서는 `Task`/`Task<T>`와 적절한 `CancellationToken`을 사용하고 오류·취소의 계약을 명확히 한다. 동기 API만 필요한 라이브러리를 무조건 `Task.Run`으로 감싸지 않는다. 공유 상태의 동시 접근은 소유권과 동기화 방식을 정하고, 외부로 노출한 API의 스레드 안전성 가정을 기록한다.
- 이벤트 핸들러 외에는 `async void`를 사용하지 않는다. 비동기 작업의 예외를 관찰하고 동기 대기로 인한 교착 상태를 피한다.

## WinForms UI 작업에만 적용: Visual Studio 디자이너 계약

UI가 없는 작업에는 이 절과 아래의 UI 응답성 절을 적용하거나 UI 산출물을 요구하지 않는다.

- 폼, `UserControl`, 컨트롤 배치, 속성과 이벤트 연결은 사용자가 Visual Studio 디자이너의 편집 화면·속성 창·이벤트 탭에서 열고 수정할 수 있도록 구현한다. 프로젝트의 디자이너 생성 구조, 직렬화 규칙과 partial 클래스 경계를 따르면 `.Designer.cs`와 `.resx`를 코드로 편집해도 된다. 업무 로직과 런타임 전용 작업은 디자이너 관리 초기화 코드 밖에 둔다. 디자이너에서 지원하는 배치·설정·이벤트 연결을 런타임 전용 코드로 옮겨 사용자 편집을 막지 않으며, 본질적으로 런타임 코드가 필요한 부분은 이유와 범위를 설명한다.
- 구성형 UI는 디자이너 디자인 화면에서 열 수 있는 `UserControl`을 우선 검토한다. 커스텀 그리기 등으로 디자이너 배치가 불가능할 때만 필요한 범위에서 코드 기반 UI를 쓴다. 디자인 시 생성자·속성 설정·`Load`가 장치 연결, 네트워크 요청, 장시간 작업, 런타임 전용 서비스나 모달 UI에 의존하지 않게 한다.
- `UserControl` 및 커스텀 UI의 공개 사용자 정의 옵션은 프로젝트에서 정한 **하나의 옵션 카테고리**(예: `Coffee Options`)로, 사용자 정의 이벤트는 그와 구분되는 **하나의 이벤트 카테고리**(예: `Coffee Events`)로 묶는다. 기존 카테고리 이름이 있으면 재사용한다. 각 멤버에 `Category`와 의미 있는 `Description`을 지정한다. 사용자 정의 이벤트는 표준 .NET 이벤트로 노출하여 디자이너의 **이벤트 탭**에서 핸들러를 생성·수정할 수 있게 한다.
- 프로젝트 기존 패턴이나 구체적인 요구로 옵션 객체가 필요할 때만 확장 가능한 공개 옵션 객체를 사용한다. 옵션 타입의 `ExpandableObjectConverter`, 속성의 `DesignerSerializationVisibility.Content`, 적절한 `Browsable`·기본값·직렬화 규칙을 적용한다. `DefaultValue` 특성이 런타임 값을 초기화하지 않는다는 점을 확인하고, 필요한 경우 `ShouldSerializeX`/`ResetX` 패턴을 사용한다. 단순 속성이면 카테고리만으로 그룹화한다. 사용자가 편집한 설정 값이 저장 후에도 유지되도록 디자이너 직렬화 규칙을 지킨다.
- 에이전트가 디자이너를 직접 열어 컨트롤 추가, 속성 변경, 이벤트 연결, 저장·재열림을 확인하거나 컴퓨터유즈로 자동 조작할 필요는 기본적으로 없다. 코드 검토로 디자이너 호환성을 확인하고 사용 가능한 도구로 변경 프로젝트를 빌드한다. 사용자가 직접 확인을 명시적으로 요청했거나 구체적인 디자이너 결함을 코드 검토·빌드만으로 해결할 수 없을 때만 실제 디자이너 확인을 수행한다. 디자이너 접근 제한만으로 UI 구현을 차단하지 않으며 실제 확인 여부를 구분해 보고하고 미검증 결과를 확인한 것처럼 주장하지 않는다. 최신 .NET의 디자이너 확장이 꼭 필요한 경우 .NET Framework 전용 예제를 그대로 복사하지 말고 대상 Visual Studio/.NET 조합의 호환성을 확인한다.

## UI 응답성과 작업 수명

- UI 스레드에서 장시간 I/O, 동기 장치 호출, CPU 집약 계산, 대기·잠금·`.Result`·`.Wait()`을 수행하지 않는다. I/O에는 가능한 한 실제 비동기 API와 `await`를 사용한다. CPU 작업 또는 비동기 API가 없는 장시간 동기 SDK 작업은 장치의 스레드 제약을 확인하고 UI 밖의 적절한 작업자에서 실행한다. 모든 작업을 무조건 `Task.Run`으로 감싸지 않는다.
- UI 이벤트 핸들러가 시작한 작업은 취소·타임아웃·예외·중복 실행·완료 후 UI 상태 복원을 처리한다. 장시간 작업의 `CancellationTokenSource` 수명을 폼/컨트롤 수명과 연결하여 닫힘·해제 시 취소한다.
- 백그라운드 작업에서 WinForms 컨트롤에 직접 접근하지 않는다. .NET 9 이상에서는 기존 프로젝트와 호환될 때 `Control.InvokeAsync`를 우선 검토하고, 그 밖에는 대상 프레임워크와 기존 패턴에 맞는 UI 스레드 전환 방식을 쓴다. UI 콜백은 짧게 유지하고, 컨트롤이 이미 닫히거나 해제된 경우를 처리한다. 진행률 갱신 빈도도 UI가 느려지지 않게 제한한다.
- UI 응답성은 실제 작업 중 클릭·스크롤·창 이동·닫기, 오류·취소 경로에서 확인한다. 절대적인 무지연 수치를 가정하지 말고 발견된 멈춤이나 병목을 수정하고 재검증한다.

## 검증과 종료 보고

- 정확한 대상 솔루션·구성(Debug/Release)·플랫폼(x64 등)으로 빌드하고, 변경한 프로젝트에 새 컴파일러/nullable/분석기 경고를 남기지 않는다. 기존 경고는 기준 상태와 구분해 보고한다. 변경된 순수 로직은 프로젝트의 기존 테스트 방식으로 성공·실패 경계를 검증한다. 외부 SDK·카메라·네트워크 변경은 가능한 실제 Debug 실행에서 초기화, 정상 동작, 실패, 취소·종료, 리소스 해제를 확인한다.
- UI 변경은 디자이너 호환 초기화 구조, 편집 가능한 속성·이벤트 메타데이터, 직렬화와 런타임 로직 분리를 코드로 검토하고 사용 가능한 도구로 빌드한다. 실제 Visual Studio 디자이너 확인은 사용자의 명시적 요청이나 구체적인 디자이너 결함 해결에 필요한 경우 외에는 필수가 아니다. 코드·빌드 근거와 실제 디자이너·실행 검증을 구분해 보고한다. 빌드만으로 실제 디자이너 동작이나 UI 응답성을 확인했다고 보고하지 않으며 수행하지 않은 검증을 통과로 표시하지 않는다.
- 단독 작업에서는 담당 에이전트가 변경 파일, 재사용 근거, 실제 검증 결과, 미검증 범위와 위험을 확인하고 종료 결과를 보고한다. 다중 에이전트 작업에서는 각 담당자가 같은 내용을 PM과 QC에 전달한다. QC는 확인 가능한 결함과 제안을 구분하고, PM은 모든 완료 기준과 QC 재검증 결과를 직접 확인한 뒤 종료한다.
