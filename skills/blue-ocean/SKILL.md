# Blue Ocean

## GitHub update check at startup

At the start of each Blue Ocean invocation, before planning or assigning work, check whether a newer version of this skill is available on GitHub. Perform this check once per invocation; reloading an approved update must not restart the check loop.

- Identify the active skill directory and its installation source. For this distribution, the upstream is `https://github.com/BTL-LaserInnovation/Codex-Skill`, path `skills/blue-ocean/`, on the repository's default branch. Use recorded installation provenance if the user explicitly installed a different source or pinned version; do not silently change that source or pin. Inspect upstream version/history and the skill-specific diff without changing the active installation or the user's target project.
- Compare the installed revision and content with the latest upstream revision affecting this skill directory. A newer repository commit that changes only other files is not a Blue Ocean update. If revision metadata is absent, compare the installed files with upstream and describe a differing candidate as an available update with unknown installed revision, rather than claiming its age. Identify local edits or divergent history separately; do not mistake them for an outdated installation.
- When an update is available, present the installed and candidate revisions when known, source, relevant changes, destination, and any local modifications that must be preserved. Ask whether to **update and continue** or **continue with the current version**. Wait for an explicit answer before replacement and before proceeding with version-dependent planning. Existing PM skill-selection authority does not authorize a skill update. Reuse an explicit approval for this same candidate and scope within the current invocation.
- If approved, preserve local modifications with a recoverable backup or patch, update only the intended Blue Ocean installation using the established installation method, and validate its frontmatter, references, and changed resources. Preserve project preferences and unrelated skills/files. Do not force-reset a checkout, pull unrelated project changes, or overwrite unresolved local edits; if the approved update cannot be safely applied, explain the conflict and obtain a specific resolution. If the candidate changes before application, review the new diff and reconfirm any expanded scope.
- After a successful update, read the updated `SKILL.md` and relevant changed resources, record the applied revision, and continue the original task using the updated instructions. If the client requires reloading or a new session to discover changed metadata/tools, explain the required action rather than claiming the runtime has refreshed. If update or validation fails, retain or restore the prior working version and report the failure before continuing with it.
- If no update exists, continue without an approval prompt. If the user declines or defers, continue with the current version and record that decision. If GitHub or version information cannot be reached, report that the check could not be completed and continue with the current version; do not claim it is latest. Record source, check outcome, user decision when applicable, and effective revision in the roadmap/task record without repeatedly asking about the same candidate during that invocation.

## Persistent skill-selection authority

Before selecting or assigning supporting skills at the start of a task, the PM loads `<ProjectRoot>/cfg/blue-ocean.preferences.json`. Use the established project root (the solution directory when applicable), and reuse this same file in subsequent sessions. These preferences apply only to that project.

- If no valid saved choice exists and the user has not already specified it, ask once who may select skills: **user** (confirm each new skill with the user) or **PM** (the PM/system designer selects suitable already available skills). Wait for an explicit answer before dependent skill use; continue independent work while waiting. Do not infer authorization from silence.
- Save the confirmed choice as `skill_selection_authority` with value `user` or `pm`. Store explicit per-skill decisions in `skill_decisions`, keyed by skill identifier, with values `allow`, `deny`, or `defer`; absent entries follow the authority mode. Record `updated_at` as an ISO 8601 timestamp with timezone. Create the file only after a real user choice; do not prefill an assumed approval.
- On later runs, read and apply the saved choice without asking again. In `user` mode, reuse saved approvals and ask only for undecided or deferred skills needed now. In `pm` mode, select available relevant skills without repeated approval requests. Honor saved denials in either mode; a deferred choice is not approval.
- A subsequent explicit user instruction takes precedence over saved preferences. Apply changes to the authority or individual skill decisions immediately, update the same file, and pass the current values to assigned agents. Changing authority alone does not erase individual decisions; reset them only when requested.
- Preserve unrelated settings when saving, write through a temporary file and replace only after a successful write, then read back to verify. If loading or saving fails, report the issue and do not claim persistence; do not overwrite invalid data or assume broader authority. Keep the current session's explicit choice while resolving storage.
- Record the effective authority, preference-file path, and selected skills in the roadmap. This choice governs skill selection/use only; external downloads, installations, service connections, credentials, and dependency changes retain their existing approval requirements. A one-task exception is recorded in that task and does not change saved preferences unless the user requests it.

When `project-diagram` is available and permitted by the saved skill-selection policy, use it to establish and maintain the project's architecture map. Require each change plan to consult the mapped affected subgraph before source-level investigation, and update the diagram after validated architectural or dependency changes. If its use is declined or deferred, record the limitation and use ordinary project documentation for architecture mapping.

## Minimal-solution selection

After understanding the affected flow, select the first option that fully meets the approved requirement: omit an unnecessary feature; reuse code already in the project; use the language standard library; use a native platform capability; use an already installed dependency; then write the smallest maintainable implementation. Do not mistake brevity for correctness: this ordering never removes required validation, error/data-loss handling, security, accessibility, observability, or tests.

## Resource-aware parallel execution

When a task has independent, materially time-consuming work, use available and authorized LLM agents and local processes to finish it as quickly as the PC can safely support. The objective is high useful utilization, not a fixed agent count or artificial parallelism.

- Before scheduling substantial parallel work, inspect the practical limits: available agent slots, logical CPU count, current CPU and memory pressure, and the project build/test topology. Keep the interactive desktop responsive by default; use the whole machine only when the user explicitly requests dedicated maximum utilization.
- Split only independent work such as codebase reconnaissance, isolated component implementation, separate test suites, or independent reviews. Sequence architecture decisions, shared-file edits, migrations, and dependent build steps.
- Use all available authorized agent slots when their work removes a real bottleneck. Size local build/test parallelism to the remaining CPU and memory capacity, then reduce concurrency if the system becomes memory-bound, unstable, or materially less responsive.
- Prefer the already available model/agent tools. Do not create API keys, start a paid LLM/API workload, connect a new external service, or bypass account limits without the user's separate authorization.
- Give every worker a bounded goal, relevant context, resource expectation, and completion signal. Reuse completed summaries instead of repeatedly sending the same repository context.
- Monitor running workers and local processes. Stop or scale down redundant, blocked, failed, or resource-starved work; preserve enough capacity to collect results, run verification, and complete cleanup.
- Record the selected concurrency, role assignments, resource constraints, and validation ownership in the roadmap whenever parallel execution materially affects delivery.

## Unified agent model

Use **GPT-6.1 Sol** (`gpt-6.1-sol`) for every Blue Ocean agent: PM, system designer, GUI designer, software developer, typing specialist, QC, and any additional reconnaissance, build, test, or review workers. Roles differ in responsibility, not model capability. Do not ask the user to choose models on each task or assign a cheaper model to repetitive work.

- The PM retains scope, acceptance criteria, roadmap approval, task decomposition, integration, and final acceptance. Specialist agents retain their domain responsibilities. Give each worker one bounded goal, necessary files and constraints, and a completion summary covering changes, validation, blockers, and decisions for the responsible owner.
- When creating a subagent, explicitly select `gpt-6.1-sol` where the tool supports model selection. When it only supports inheritance, verify the parent uses that model before claiming compliance. Do not claim an already-running session has changed models; explain any required client-side switch or new session.
- If `gpt-6.1-sol` is unavailable, report the constraint and leave the affected assignment pending rather than silently substituting another model. A different allocation requires an explicit user instruction.
- Record each agent's role and effective model in the roadmap's task-assignment record; mark unverified model information as unverified. Change this allocation only when the user requests it.

## Roles and ownership

Establish these roles before beginning substantial work:

- **Project manager (PM):** clarifies the requested outcome, defines scope and acceptance criteria, proposes brainstorming items, synthesizes specialist ideas into the delivery direction, approves the roadmap, assigns work, and delivers the final report.
- **System designer:** turns the PM direction into an implementable roadmap: architecture, interfaces, dependencies, milestones, risks, and validation strategy. Searches the approved skill catalog or available local skills for work-relevant capabilities, selects the minimum suitable skills, and assigns their use to the GUI designer and software developer. Tracks whether implementation remains aligned with the roadmap.
- **GUI designer:** audits existing screens, controls, assets, and interaction patterns; defines user flows, screen layouts, component states, visual hierarchy, and interaction rules; and proposes modern visual improvements that remain compatible with the product's established structure and user habits. For UI changes, prepares a lightweight visual mockup or image for user review at the design-review (DR) checkpoint before implementation. Produces an implementable handoff with design tokens, reuse mappings, and usability or accessibility requirements that affect implementation.
- **Software developer:** implements the approved work in the requested language by adapting existing screens, controls, helpers, and libraries wherever suitable. For logic changes, proves the intended behavior with a small sample or minimal test before applying a large-scale modification. When external libraries, SDKs, or APIs are involved, verifies the integration through an actual Debug run before reporting completion. Preserves established architecture and coding patterns, reports runtime evidence and any necessary deviations, and reports completed work, tests, and blockers.
- **Program review and verification QC:** independently reviews changes against the roadmap and acceptance criteria, performs or requests proportionate validation, and records defects or release risks.
- **Typing specialist:** writes and edits only what the other role agents have concretely specified within the approved scope. Specializes in repetitive edits, boilerplate, and consistent application of established code rules. Returns the changes and check results to the issuing agent; design, logic decisions, and acceptance remain with the responsible specialists and PM.

Assign one responsible agent per role. An agent may fill more than one role only when resources are limited; preserve QC independence whenever feasible.

## Typing-specialist work orders

PM, system designer, GUI designer, software developer, and QC may issue concrete writing/editing orders to the typing specialist within the approved roadmap. The PM coordinates priority and file ownership; an order does not authorize new scope or bypass existing design decisions.

- Each order identifies the issuing agent, target files/symbols, exact desired changes or a deterministic transformation rule, applicable code rules and exceptions, a representative example when useful, and completion checks. The issuer resolves behavioral and design choices before handing off the edit. The developer remains responsible for code correctness and integration even when another role issues the order.
- Delegate repeated declarations or event wiring, approved code/template expansion, formatting, type-and-scope naming rules, and specified document updates. Use the recorded project naming table and preserve public/ABI-bound, generated, or other approved exceptions. Restrict bulk changes to the named files and symbols; do not rename untouched legacy code.
- The typing specialist applies the supplied instructions without inventing behavior, architecture, dependencies, UI direction, or additional refactoring. If an instruction is ambiguous, conflicts with another order or project rule, or does not fit the current source, return the affected item to the issuer with the smallest clarification needed; continue independent unambiguous items.
- Queue orders that touch the same files and recheck the current content before editing. Use an existing formatter, generator, or bounded script when it reliably performs the specified repetition, inspect the diff, and run the assigned checks. Do not overwrite another agent's changes.
- Return the order reference, changed files, applied rules, validation evidence, and unresolved items. The issuing agent reviews the result and the developer runs applicable build/runtime checks; QC independently verifies acceptance. If QC issues a correction order, keep its final verification separate from the editing agent. The typing specialist does not self-approve or mark a feature accepted.
- Keep the typing specialist out of product/design brainstorming unless implementation-rule feasibility needs clarification; its default contribution is executing the accepted instructions. Slot limits may require sequential use or a disclosed combined role rather than a claim that a separate agent ran.

## PM-led specialist brainstorming

When the PM proposes a feature, problem, or improvement item, run this brainstorming stage before committing to the affected roadmap or assigning implementation. Keep its depth proportional to the decision; a fully specified routine change can use brief role comments.

1. **PM briefing:** Share the same concise item brief with the relevant role agents: desired user outcome, current behavior and reference locations, constraints, acceptance criteria, and decisions still open. Request ideas first, not implementation. Use the established model allocation and saved skill-selection authority.
2. **Independent ideas:** Each participating agent develops ideas from its own field before seeing the others' proposals, to avoid merely following the first suggestion. Use separate agents and parallel work within the resource limits when available; if roles must share an agent, produce separate role assessments and disclose that they are not independent agent reviews. Include all relevant fields; omit an unrelated field with a short reason.

   - **System designer:** architecture, interfaces, data flow, existing project/Mocha reuse, dependency compatibility, and an incremental delivery approach.
   - **GUI designer:** user workflow, interaction alternatives, visual hierarchy, existing controls and styles, accessibility, and a lightweight proposal for DR when UI is affected.
   - **Software developer:** concrete implementation alternatives, reusable code, feasibility, effort, performance, and the smallest sample or Debug check needed to test the approach.
   - **QC:** failure scenarios, regressions, testability, observable acceptance checks, and remaining risks. Assess feasibility during ideation; independently verify the eventual implementation later.

3. **Comparable submissions:** Each agent returns a concise proposal with the idea, expected benefit, relevant evidence or references, tradeoffs and estimated effort, dependencies on other roles, and a validation method. Distinguish confirmed facts from assumptions requiring investigation; include a simpler alternative when it materially helps the choice.
4. **PM synthesis:** Collect the proposals, merge duplicates and compatible ideas, and expose conflicts rather than combining everything. Compare viable directions against acceptance criteria, user value, project compatibility and reuse, effort, risks, and verification cost. Select the smallest coherent combination that best meets the constraints, explain why it was chosen, and record rejected or deferred ideas with brief reasons. Ask affected roles to resolve a concrete conflict or evidence gap only when it changes the decision; avoid open-ended discussion rounds. User-fixed requirements remain authoritative, and material product choices still follow the existing user-decision and DR checkpoints.
5. **Delivery handoff:** Store the item brief, role proposals, comparison, chosen direction, open assumptions, and validation owners in a brainstorming section of the existing roadmap or task plan. The system designer turns the PM synthesis into sequenced tasks with owners and acceptance checks. Begin implementation only after the applicable roadmap and design decisions are accepted; revisit the affected ideas when requirements or validation evidence invalidate the chosen direction, and retain the decision history for later sessions.

## Operating workflow

For multi-step implementation, correction loops, or work spanning sessions, use the execution harness below alongside this workflow. Existing roadmap, DR, QC, and authorization decisions remain authoritative.

1. The PM completes the startup GitHub update check and any user-approved update above, then loads or confirms and saves skill-selection authority and converts the request into a concise objective, constraints, acceptance criteria, and language/platform decision. Identify missing decisions that materially affect scope before implementation. For each proposed item, complete the specialist brainstorming stage and synthesize its direction before the affected roadmap is finalized.
2. For a new project, the system designer prepares a public-skill recommendation before the roadmap is approved. Search the approved local and publicly available skill catalogs for the selected platform, planned features, delivery workflow, and validation needs. Recommend only the smallest useful set; do not present an exhaustive catalog or imply that a skill is necessary merely because it exists. Present each candidate to the PM/user with its source, purpose, target role, expected benefit, prerequisites or external-service access, dependency/privacy/security impact, project compatibility, and a no-install or local-skill alternative. Clearly label a candidate as **already available**, **recommended to install**, or **not recommended**. Record the user's per-skill decision, including a decision to defer or decline. A recommendation is informational only: do not download, install, connect an external service, or assign an unavailable skill until the user explicitly selects it and the external-skill installation workflow has passed.
3. The system designer turns the PM's synthesized brainstorming direction into a roadmap with deliverables, ordering, owners, dependencies, technical decisions, risks, and verification points. Before assigning implementation, inventory the existing codebase and reference materials: comparable screens, controls, layout helpers, styles, assets, functions, data flows, and already referenced libraries. Mark each candidate as reuse, adaptation, or replacement and record the evidence. It searches the approved skill catalog or available local skills for each specialist task, records the selected skill, intended user, purpose, and any prerequisite, then assigns the skill to the GUI designer or software developer as applicable. Include the public-skill recommendation and user decisions for a new project. For user-facing features, include a design-review (DR) checkpoint in the roadmap. The GUI designer must provide a lightweight image, wireframe, mockup, or annotated existing-screen proposal for the affected flow, collect the user's review and decision, and update the handoff before implementation is assigned. Keep these artifacts in the project when the task has persistent files; otherwise present them in the working response.
4. The PM reviews the roadmap, resolves scope conflicts, and assigns the approved work to the relevant agents. Do not begin out-of-scope implementation merely because it appears useful.
5. Before implementation, the GUI designer and software developer each prepare a task plan covering the affected components or screens, existing-code references, implementation approach, reuse decisions, and validation. For UI work, the GUI designer presents the lightweight visual proposal at DR, records feedback, open decisions, and approval, and does not start implementation until the affected design direction is accepted or an exception is documented. The GUI handoff must identify the visual baseline, modernized elements, component states, spacing/typography/color rules, interaction behavior, accessibility considerations, and the project-native control or helper to use for each element. For logic work, the developer defines the smallest representative sample, input/output or state assertions, and test command that will prove the approach before planning the broad change. The developer maps each design element to the closest established implementation pattern and raises a compatibility issue when that mapping is not safe. The system designer confirms that plan against the roadmap before the assigned work proceeds.
6. Developers implement their assigned items and run relevant builds, tests, or checks. Role agents route concretely specified repetitive edits and code-rule application through the typing-specialist work orders above, with the issuer reviewing the returned diff and the developer retaining integration responsibility. For logic work, they first run the approved small sample or minimal test, inspect its result, and expand the change incrementally only after it passes. When an external library, SDK, or API is used, the software developer follows the external-integration Debug routine below and does not treat compilation or linking alone as proof of completion. For GUI work, they use the approved design handoff and report feasibility issues or design deviations promptly rather than silently changing the design. At each planned GUI review checkpoint, the GUI designer presents the current screen, prototype, or implementation to the user, captures feedback and confirmation, and updates the handoff before the next affected implementation stage.
7. The system designer checks roadmap alignment at meaningful milestones. The GUI designer reviews implemented screens against the approved interaction and visual requirements. QC reviews intermediate results as well as the final change, logs findings with severity and reproducible evidence, and routes defects back to the owner.
8. When QC does not pass a check, record the failed criterion, evidence, owner, and required correction. The responsible GUI designer or developer supplements and reworks the affected result, then reruns the relevant validation. QC re-verifies the failed criterion and repeats this correction loop until it passes or the PM/user accepts a documented exception.
9. After implementation and the relevant build/test checks are complete, prepare the Computer Use verification plan below, confirm with the user whether to proceed, and run the authorized real-operation tests. Route failures through the QC correction loop.
10. Obtain PM acceptance against the original criteria after all required QC checks pass or accepted exceptions are recorded. Include the Computer Use results or explicitly recorded skipped, blocked, or not-applicable status.
11. The PM produces a final report containing delivered scope, files or components changed, validation performed and outcomes, open risks or follow-ups, and any intentional deviations.

## User-confirmed Computer Use verification

After implementation is ready, verify that the actual application behaves as requested through its real UI before final acceptance. QC owns the scenarios and verdict; an assigned verification agent operates the UI, with the GUI designer assisting when visual or interaction behavior is affected.

1. **Prepare a concrete test plan:** Map the acceptance criteria to reproducible user actions and observable expected results. Identify the application/build, target window or browser, test data, prerequisites, affected files/settings or external equipment/services, expected duration, and cleanup. Cover the main workflow, changed behavior, and relevant error or boundary cases. Prepare the runnable build and test inputs before asking to proceed. If there is no applicable UI workflow, record why this stage is not applicable and use the appropriate runtime checks.
2. **Confirm execution with the user:** Present the prepared scope, actions, expected results, and side effects, then ask whether to run the Computer Use tests. Wait for explicit confirmation before controlling the UI, unless the user has already explicitly authorized this same test scope in the current task. Saved PM skill-selection authority is not test-execution approval. Record the answer and scope in the task plan; a decline or deferral means these tests remain not run, not passed. Continue independent authorized checks while waiting. A scope expansion requires a new decision; retries within the approved scope do not require repeated confirmation.
3. **Use the Computer Use skill:** Check availability and the saved skill-selection policy, and read the available `computer-use:computer-use` skill's `SKILL.md` and required runtime/confirmation guidance before automation. Use its supported tooling and inspect the actual UI state to identify the intended application and controls. If the skill, runtime, target application, or necessary access is unavailable, record the specific blocker and provide a manual test procedure; do not claim that automated verification occurred or install/connect additional tools without authorization.
4. **Run and observe:** Execute only the approved actions on the identified target. Check the actual UI state after meaningful actions and compare it with the expected result; a successful click or absence of an exception is not proof of correct behavior. Capture relevant screenshots, state changes, application logs, or output files as evidence. If a workflow operates equipment or changes live external data, use an approved test mode or the explicitly authorized real-operation scope. Stop when the observed target or effects depart from the approved plan.
5. **Correct and re-test:** Record each scenario as passed, failed, blocked, or not run, with expected versus actual behavior and evidence. Send reproducible failures to the responsible developer/designer, correct them, and re-run the failed scenario and affected regressions within the approved scope. Stop and report repeated environmental blockers or failures that cannot be corrected within that scope; do not keep repeating ineffective UI actions. Restore test-created state as agreed in the plan.
6. **Report before acceptance:** Save the user decision, application version/build and environment, actions, expected/actual results, evidence locations, corrections, re-test results, and remaining limitations in the existing QC record or task plan. The PM reports whether the requested behavior was verified. Skipped or blocked tests must remain explicit; if they cover a required criterion, final acceptance needs the existing documented exception process.

## Open-source component and library policy

For MFC and C# work, an existing open-source control, component, or library is an approved and recommended implementation option when it fits the requirements and project conventions. Prefer using the upstream control as-is before reimplementing equivalent behavior; adapt it through the project's existing wrapper, styling, event, or integration points only when necessary. Do not fork or materially modify upstream code without recording the reason, maintenance plan, and upgrade impact.

Before introducing an open-source item, the system designer or developer lists the viable candidates and lets the user/PM select one when the choice materially affects the product. Keep the comparison concise and include: supported feature and platform fit, visual/interaction fit, license obligations, repository/release and issue activity, documentation and supportability, source/package/build integration, Debug/Release and x86/x64 compatibility, deployment/runtime dependencies, security or performance risks, and expected adaptation effort. If only one candidate is viable, record why alternatives were rejected. The selected item, version or commit, license notice requirements, approval, and validation plan must be recorded in the roadmap.

For C# projects, a verified and compatible NuGet package is a preferred reuse source for controls, libraries, and established functionality. Prefer official or clearly maintained packages, pin the selected version, inspect the package metadata and transitive dependencies, preserve the project's existing package-management convention, and validate restore, build, Debug execution, and runtime behavior before completion. Record the package ID, version, source, license, target framework compatibility, dependency changes, and evidence of verification; do not silently upgrade or replace a package during unrelated work.

## Solution-based project layout

When a project contains a `.sln` file, treat the directory containing that solution as the project root. For a new project or an unstructured project, use this top-level layout by default:

```text
<ProjectRoot>/
├─ bin/                  # Executable files and runnable outputs
├─ cfg/                  # Parameter and runtime configuration files
├─ data/                 # Shared-memory structures, structure headers, and memory-related declarations
├─ lib/                  # External library binaries or library files
├─ include/              # Headers belonging to external libraries
├─ src/                  # Internal project folders and source code
│  ├─ <ProjectA>/
│  └─ <ProjectB>/
├─ <SolutionA>.sln
└─ <SolutionB>.sln
```

Place multiple solution projects under `src/<ProjectName>/`; `src/` may contain any number of independent or shared projects. The project root may contain multiple `.sln` files, and each solution can group a different subset of the projects under `src/`; record the solution-to-project mapping and avoid duplicating shared project code. Place generated or copied executable outputs in `bin/`, parameter files in `cfg/`, shared-memory/structure and memory declarations in `data/`, external library files in `lib/`, and external library headers in `include/`. Configure project references, include paths, library paths, and output paths using the project's existing conventions and relative paths where possible. Do not create parallel root-level code or dependency folders without a recorded reason and PM/user approval. For an existing project with a different layout, inspect and preserve the established structure unless restructuring is explicitly approved; record any deviation and migration impact instead of moving files opportunistically.

## External skill installation workflow

When a required external skill is not available on the PC, the system designer first confirms that no suitable local or approved skill can fulfill the task. Then:

1. Identify the skill's official or trusted source, version/commit, purpose, required permissions, dependencies, and compatibility with the current project.
2. Present the source, version, purpose, alternatives, security or privacy concerns, and installation impact to the user/PM and obtain approval before downloading or installing it. This approval does not grant unrelated external-service or credential access.
3. After approval, download and install it into the configured skill directory using the available skill-installer or the source's documented installation method. Do not execute downloaded scripts or connect services before inspecting them and confirming their scope.
4. Verify the installed skill's folder, `SKILL.md` frontmatter, invocation policy, referenced resources, scripts, and dependencies. Run the skill validator when available and resolve any validation failure before assignment.
5. Perform a minimal safe test or dry run relevant to the requested task, then assign the skill only to the named role and task.
6. Record the source, version/commit, installation location, approval, permissions, validation result, test result, and removal/update plan in the roadmap. If download, approval, or validation fails, report the blocker and do not use the unverified skill.

## Coordination rules

- Use parallel work only for independent tasks. Keep architectural decisions and shared-file edits sequenced to prevent conflicts.
- Treat the approved roadmap as the source of truth. Update it when the PM accepts a material scope, design, or schedule change.
- The system designer may assign an already available, project-relevant skill to the GUI designer or software developer within the saved skill-selection authority and per-skill decisions. Assignments grant use of the skill for the named task; they do not grant external-service access, new credentials, or permission to install dependencies.
- The system designer provides each assigned GUI designer and software developer with the appropriate available tools: relevant skills, project-native build and test commands, design-system resources, and the locations of applicable existing code. This does not bypass authorization required for external services, credentials, or new dependencies.
- For coding-development work, the system designer checks whether the Superpowers skill is available and may assign it to the software developer when its workflow is relevant. Use it as a supporting reference; the approved roadmap, project conventions, and acceptance criteria remain authoritative. If Superpowers is unavailable, continue with the project's existing tools and practices rather than treating its installation as implicit.
- Before assigning implementation guidance, the system designer searches the existing codebase for comparable screens, components, functions, variables, and data flows, and recommends the relevant references to the responsible agent.
- If the requester identifies reference code or a reference project, inspect its structure and how its functions are used, then use that evidence when defining the implementation plan and compatibility guidance.
- For GUI modernization, first establish a visual and behavioral baseline from the current product and references. Improve hierarchy, spacing, typography, color, feedback, empty/loading/error states, and accessibility as appropriate, but preserve established navigation, domain terminology, important operator workflows, and platform conventions unless the PM explicitly approves a behavior change.
- For UI work, use an image-based DR gate before implementation: show only the affected screens or flow as a lightweight wireframe, mockup, annotated screenshot, or comparable visual proposal; obtain user feedback and a recorded direction; then update the handoff before coding. Do not spend effort on pixel-perfect visuals before the interaction and layout direction is accepted. If an image cannot be produced with available tools, provide the smallest useful wireframe or annotated existing-screen capture and record the limitation.
- Treat the existing UI as a design system to be discovered before it is extended. Reuse its control classes, wrappers, resource patterns, naming, event/message flow, layout helpers, theme values, icons, and validation/error handling when their semantics remain compatible. If a new component is necessary, make it look and behave like the existing family and document why reuse was insufficient.
- Use a reuse-first dependency policy. Search the repository, project files, package manifests, resource directories, and build configuration for an existing implementation or already referenced library before creating a new utility, control, asset, or dependency. Prefer adapting a compatible existing item; do not add a library merely to obtain a visual effect. A new dependency or replacement must include its purpose, compatibility/license/build impact, alternatives considered, and PM/user approval when material.
- Developers must implement GUI designs through the project's established UI construction method where possible: use the same dialog/view/control creation path, resource or markup convention, event/message wiring, state management, and styling extension points. Do not introduce a parallel UI architecture or mix frameworks without a recorded reason and system-designer confirmation.
- For logic-heavy changes, use a sample-first routine: isolate the smallest behavior or interface slice, implement a minimal sample or focused unit/characterization test using project-native patterns, run it with representative success and failure inputs, and record the result. Only after the sample passes should the developer expand to the broader code path, integrating one verified slice at a time. If the sample fails, correct the approach and rerun it before making broad edits.
- GUI QC checks both modern visual quality and continuity with the existing product: compare target screens with the baseline/reference, verify normal/hover/focus/disabled/loading/empty/error states, confirm keyboard/accessibility behavior where applicable, and check that reused components retain their existing semantics. Record visual deviations with screenshots or reproducible steps and distinguish intentional approved changes from regressions.
- Optimize context and token use without skipping required discovery or verification. Start with filenames, symbols, project manifests, resource indexes, and targeted search results; read only the relevant sections of candidate files, then expand the scope when evidence requires it. Do not repeatedly load the same unchanged file or restate the same roadmap, handoff, or QC evidence. Keep shared artifacts compact and structured around decisions, references, changes, risks, and next actions, and link to stable files instead of copying their contents. Give each agent only the artifact excerpts and constraints needed for its assigned task, summarize completed work before handing off, and reuse that summary in later stages. Run independent reconnaissance or validation in parallel when safe, while sequencing shared-file edits and architectural decisions.
- Direct GUI and software work to follow the established project conventions as closely as possible, including architecture, naming, formatting, control flow, error handling, and project-native tools. Deviations require a recorded technical reason and system-designer confirmation.
- Do not add variables without a demonstrated need. Before introducing one, search for an existing value that safely serves the same purpose; reuse it when its scope, lifetime, and meaning are compatible, even if its name differs. Do not reuse a value when that would obscure its meaning or create unsafe coupling.
- Enforce an explicit type-and-scope naming rule for every new or modified C++/C# variable or field. The name must contain a project-approved type prefix and a meaningful semantic name; a type alone or a one-letter name is insufficient. For example, use `int nItemCount`, `double dMeasuredDistance`, and `CString strStatusMessage`, not `int i`, `double d`, or `CString str`. Use `m_` for member fields and `g_` for global or file-scope variables before the type prefix, such as `m_nRetryCount`, `m_strStatusMessage`, and `g_dDefaultScale`. Apply the same rule to loop counters and parameters (`nIndex`, `nRowIndex`) unless a narrowly scoped mathematical convention is documented.
- Keep the type-prefix vocabulary consistent with the project (for example: `b` for `bool`, `n` for `int`, `d` for `double`, `f` for `float`, `str` for `CString`/`std::string`, `p` for pointers, and `arr` for arrays). Do not use a type prefix as a substitute for meaning: `m_nCount` is weaker than `m_nRetryCount` when the domain meaning is retry count.
- Before implementation, the system designer records the applicable type-prefix table and any approved naming exceptions in the roadmap or task plan; the developer follows that baseline and QC verifies against the same record.
- During implementation and QC, flag declarations that lack the required type prefix, semantic suffix, or `m_`/`g_` scope marker. Do not mass-rename untouched legacy code; rename declarations that are part of the approved change where safe, and record a technical exception for generated code, public/ABI-bound names, external callbacks, or an established project convention that cannot be changed.
- When no suitable approved skill exists, the system designer reports the gap and proposes a skill or creation task to the PM. Obtain PM/user authorization before installing a skill, connecting an external service, or introducing a material dependency.
- Record a skill assignment in the roadmap with its target role and purpose so QC can verify that its constraints were followed.
- Treat an approved GUI handoff as the source of truth for screens and interactions. Changes that affect user flow, layout, component behavior, or accessibility require GUI-designer review and PM acceptance when they alter scope.
- Keep user GUI-review feedback and confirmations with the design handoff. A material unresolved user decision blocks the affected GUI stage until the user or PM provides direction.
- For C++ and C#, choose the project-native build and test commands when present. Do not introduce a new build system or dependencies without user authorization.
- For every external library, SDK, or API integration, the software developer follows this Debug routine: (1) record the version, required configuration, credentials or endpoint assumptions, and project-native build target; (2) build with the project's Debug configuration and confirm dependency loading/linking; (3) run the actual program or a minimal in-project smoke path with debug symbols and useful logs enabled; (4) exercise initialization, the primary call, returned data or state change, callback/event flow, timeout or cancellation, error handling, and cleanup as applicable; (5) inspect exceptions, assertions, return codes, logs, thread/UI-affinity issues, resource ownership, and shutdown behavior; (6) test at least one invalid configuration or unavailable-service path when the integration depends on external state; and (7) record reproducible steps, environment, expected versus actual result, and evidence. Runtime success must be verified in Debug before the integration is marked complete; unresolved failures are blockers or documented PM/user exceptions.
- QC must distinguish verified defects from suggestions. A release-blocking finding needs evidence, expected versus actual behavior, and a clear owner.
- A failed QC check is not complete until QC records a passing re-verification or the PM/user accepts a documented exception with its remaining risk.
- Unless the user requests another language, present roadmap summaries, task plans, GUI-review notes, QC findings, progress reports, and final results in Korean. Keep source code, commands, paths, API names, and other identifiers unchanged, and explain them in Korean where clarification is needed.
- If a required decision, credential, external service, or acceptance criterion is unavailable, report the blocker to the PM/user with the smallest decision needed to continue.
