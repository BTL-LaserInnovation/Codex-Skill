# GUI design and real-operation verification

Command and template paths are relative to the installed Blue Ocean skill root. Read only the sections relevant to the current task.

## User-confirmed Computer Use verification

After implementation is ready, verify that the actual application behaves as requested through its real UI before final acceptance. QC owns the scenarios and verdict; an assigned verification agent operates the UI, with the GUI designer assisting when visual or interaction behavior is affected.

1. **Prepare a concrete test plan:** Map the acceptance criteria to reproducible user actions and observable expected results. Identify the application/build, target window or browser, test data, prerequisites, affected files/settings or external equipment/services, expected duration, and cleanup. Cover the main workflow, changed behavior, and relevant error or boundary cases. Prepare the runnable build and test inputs before asking to proceed. If there is no applicable UI workflow, record why this stage is not applicable and use the appropriate runtime checks.
2. **Confirm execution with the user:** Present the prepared scope, actions, expected results, and side effects, then ask whether to run the Computer Use tests. Wait for explicit confirmation before controlling the UI, unless the user has already explicitly authorized this same test scope in the current task. Saved PM skill-selection authority is not test-execution approval. Record the answer and scope in the task plan; a decline or deferral means these tests remain not run, not passed. Continue independent authorized checks while waiting. A scope expansion requires a new decision; retries within the approved scope do not require repeated confirmation.
3. **Use the Computer Use skill:** Check availability and the saved skill-selection policy, and read the available `computer-use:computer-use` skill's `SKILL.md` and required runtime/confirmation guidance before automation. Use its supported tooling and inspect the actual UI state to identify the intended application and controls. If the skill, runtime, target application, or necessary access is unavailable, record the specific blocker and provide a manual test procedure; do not claim that automated verification occurred or install/connect additional tools without authorization.
4. **Run and observe:** Execute only the approved actions on the identified target. Check the actual UI state after meaningful actions and compare it with the expected result; a successful click or absence of an exception is not proof of correct behavior. Capture relevant screenshots, state changes, application logs, or output files as evidence. If a workflow operates equipment or changes live external data, use an approved test mode or the explicitly authorized real-operation scope. Stop when the observed target or effects depart from the approved plan.
5. **Correct and re-test:** Record each scenario as passed, failed, blocked, or not run, with expected versus actual behavior and evidence. Send reproducible failures to the responsible developer/designer, correct them, and re-run the failed scenario and affected regressions within the approved scope. Stop and report repeated environmental blockers or failures that cannot be corrected within that scope; do not keep repeating ineffective UI actions. Restore test-created state as agreed in the plan.
6. **Report before acceptance:** Save the user decision, application version/build and environment, actions, expected/actual results, evidence locations, corrections, re-test results, and remaining limitations in the existing QC record or task plan. The PM reports whether the requested behavior was verified. Skipped or blocked tests must remain explicit; if they cover a required criterion, final acceptance needs the existing documented exception process.
## Platform-specific UI workflow

Before UI implementation, if the platform or construction method is not fixed, present a concise option list covering viable project-native choices such as the C# WPF visual designer with code-behind event wiring, existing MFC DC drawing, or another requested platform. Include each option's advantages, disadvantages, compatibility impact, and estimated effort, then record the user/PM selection in the roadmap. An explicit user request takes precedence over the defaults below after feasibility and safety are checked.

Unless the user explicitly requests otherwise:

- For C# UI, use the existing WPF visual designer workflow and WPF controls, styles, and resources. By default, connect UI actions through the designer's double-click event flow so the corresponding code-behind handler is created and wired in the established project pattern. Do not use a direct XML/XAML editor as the primary UI-construction workflow; edit generated or necessary markup only when the project convention or an explicit user request requires it. Preserve an existing MVVM/command-binding convention when it is already authoritative, and record the exception to the default event-wiring method.
- For MFC UI, use the existing device-context (DC) drawing path such as `OnPaint`, `OnDraw`, or an established custom paint helper. Do not use the resource editor for new visual layout. Retain existing resource IDs, strings, images, or controls only when compatibility requires them, while keeping visual placement and rendering in the DC-based path.
- Record any platform or construction-method exception, its reason, affected files/components, and impact on maintenance or verification.
