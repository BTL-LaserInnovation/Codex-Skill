# 재사용·구현·QC 규칙

## 프로젝트 심볼 가이드

프로젝트 분석·구현 계획·소스 변경에는 [지속 허용](update-and-authority.ko.md)에 따라 설치된 `project-symbol-guide`를 적극 사용하고 변수·함수 선택 전에 해당 스킬을 읽습니다. 미설치 상태이거나 이후 사용자 제한이 있으면 대상 소스를 직접 검색하고 제약을 기록하며 설치 권한을 가정하지 않습니다.

- 기존 색인을 미커밋 변경까지 포함한 현재 소스와 대조하고 영향 클래스·모듈을 갱신합니다. 작은 수정에 전체 프로젝트 카탈로그는 필요하지 않습니다.
- 호환되는 기존 심볼의 소스 위치, 시그니처, 용도, 상태·접근·수명·스레드 제약을 추천합니다. 선택한 재사용 경로와 부족한 부분을 아키텍처·Mocha 근거와 함께 기록합니다.
- 적합한 심볼이 없으면 검색 범위·제외 후보·미확인 사항을 보고합니다. 새 프로젝트 함수를 선언·정의하기 전에는 심볼 가이드의 별도 승인 규칙을 따르며 해당 함수에 대한 기존 승인은 재사용합니다. 스킬 사용 허용만으로는 부족합니다. 필요한 새 변수에도 해당 가이드의 규칙을 적용합니다.
- 승인된 변경과 검증 후 영향 심볼·관계를 갱신하고 소스 최신 여부·검증 상태·부분 분석 범위를 구분합니다.

## Mocha 라이브러리 확인

MFC/C++의 새 컨트롤·유틸리티·라이브러리·구현을 선택하기 전에 `mocha-library`의 가용성과 저장된 권한을 확인합니다. 허용되면 해당 스킬로 `PathMocha`, 생성된 색인·관련 다이어그램, 공개 헤더·구현의 유사 동작, 후보의 빌드 계약을 확인한 뒤 구현을 배정합니다.

- 검색어·색인/다이어그램 영역·후보·선택한 재사용 경로를 기록합니다. 새 구현을 선택하기 전에 기존 후보가 부적합한 이유를 설명합니다.
- 호환되는 API·라이브러리는 공유 코드를 대상 프로젝트에 복사하지 않고 기존 계약으로 사용합니다.
- 헤더·`.lib`·`common.props`·런타임 바이너리의 Debug/Release, x64, 의존성, 배포 영향을 명시합니다.
- 무관한 대상 프로젝트 작업 중 Mocha 소스·바이너리·프로젝트·`PathMocha` 설정을 변경하지 않습니다. 불가·거절·보류 시 제약을 기록하고 일반 재사용 우선 작업을 계속합니다.

## 의존성과 오픈소스 구성요소

유틸리티·컨트롤·리소스·의존성을 추가하기 전에 저장소 코드, 프로젝트·패키지 매니페스트, 리소스, 빌드 설정을 검색합니다. 호환되는 기존 항목을 우선하며 시각 효과 하나만으로 새 라이브러리 도입을 정당화하지 않습니다.

MFC/C#에는 호환되는 오픈소스 컨트롤·라이브러리를 재사용 선택지로 권장합니다. 적합하면 원형 그대로 사용하고 기존 래퍼·스타일·이벤트로 적응합니다. 포크나 중대한 업스트림 수정은 사유·유지보수 계획·업그레이드 영향을 기록합니다.

도입 전에는 요구·시각 적합성, 라이선스, 유지보수·릴리스·이슈 활동, 문서, 패키지·빌드 연동, Debug/Release·x86/x64 지원, 배포 의존성, 보안·성능, 적응 작업량으로 후보를 비교합니다. 후보가 하나면 대안 제외 사유를 설명합니다. 중요한 제품 선택은 PM/사용자가 결정하며 목적, 선택 버전·커밋, 라이선스 고지, 승인, 검증을 로드맵에 기록합니다.

C#에서는 검증된 호환 NuGet 패키지를 우선하고 버전을 고정하여 메타데이터·전이 의존성을 확인합니다. 기존 패키지 관리 방식을 유지하고 ID·출처·라이선스·프레임워크·의존성 변경을 기록합니다. 복원·빌드·실제 Debug 동작을 검증하며 무관한 작업에서 패키지를 임의 업그레이드·교체하지 않습니다.

## Sln 기준 프로젝트 폴더 구조

`.sln`이 있으면 그 디렉터리를 프로젝트 루트로 사용합니다. 신규·미구조화 프로젝트에는 다음을 적용합니다.

| 경로 | 내용 |
| --- | --- |
| `bin/` | 실행 파일·실행 가능한 출력 |
| `cfg/` | 파라미터·실행 설정 |
| `data/` | 공유 메모리 구조체·구조체 헤더·메모리 선언 |
| `lib/`, `include/` | 외부 라이브러리 바이너리·헤더 |
| `src/<ProjectName>/` | 내부 독립·공용 프로젝트 |
| `<SolutionName>.sln` | `src/` 프로젝트를 묶는 하나 이상의 솔루션 |

솔루션·프로젝트 연결을 기록하고 공용 코드를 중복 생성하지 않습니다. 참조·Include·Library·출력 경로는 기존 관례와 가능한 상대 경로를 사용합니다. 구조 변경이 명시적으로 승인되지 않으면 기존의 다른 구조를 보존합니다. 최상위의 별도 코드·의존성 폴더는 근거와 PM/사용자 승인이 필요합니다.

## 구현 계획과 명명

- 사용자 지정 참조 프로젝트와 함수 사용 흐름을 확인합니다. 기존 화면·구성요소·심볼·데이터 흐름을 개발자에게 추천하고 변경 없는 문맥을 반복 복사하는 대신 관련 파일·발췌를 연결합니다.
- 아키텍처·서식·제어 흐름·오류 처리·프로젝트 도구를 유지합니다. 기술적 차이는 사유와 설계자 확인을 기록합니다. [개발 인계](delivery.ko.md)에 스킬·코드/설계 자료·빌드/테스트 명령을 제공하고 스킬 접근·설치는 [권한 절차](update-and-authority.ko.md)를 따릅니다.
- 사용 가능하고 허용된 Superpowers 스킬이 적합하면 설계자가 개발자에게 보조 참조로 배정할 수 있습니다. 미설치 상태가 설치 허용을 뜻하지 않으며 로드맵·프로젝트 관례가 우선합니다.
- 시각 기준, 시안 컨펌, 컴포넌트 재사용, 인계, 제작, 시각 QC는 [GUI 절차](gui-workflow.ko.md)를 따릅니다.
- 변수 추가 전에는 범위·수명·의미가 안전하게 맞는 기존 값을 재사용하되 의미가 모호해지거나 결합이 위험해지지 않도록 합니다.
- 새로 만들거나 수정하는 C++/C# 변수·필드에는 프로젝트 승인 타입 접두사와 의미 있는 이름을 사용하고 멤버는 `m_`, 전역·파일 범위는 `g_`를 타입 접두사 앞에 둡니다. 예: `nItemCount`, `dMeasuredDistance`, `strStatusMessage`, `m_nRetryCount`, `g_dDefaultScale`. 매개변수·반복문도 적용하며(`nIndex`, `nRowIndex`) 타입만 있거나 한 글자인 이름은 허용하지 않습니다.
- 구현 전에 설계자가 접두사 표·승인 예외를 기록하고 개발자·QC가 같은 기준을 사용합니다. 일반적인 접두사: bool `b`, int `n`, double `d`, float `f`, 문자열 `str`, 포인터 `p`, 배열 `arr`. 접미사에는 도메인 의미를 유지합니다.
- 영향받는 선언을 확인하되 무관한 레거시 이름은 일괄 변경하지 않습니다. 생성 코드·공개/ABI 결합 이름·외부 콜백·고정된 프로젝트 관례·좁은 수학적 표기는 기술적 예외를 기록합니다.

## 로직 샘플과 Debug 연동

C++/C#의 프로젝트 고유 빌드·테스트 명령을 사용합니다. 새 빌드 시스템·의존성에는 사용자 승인이 필요합니다.

로직 규모가 큰 변경은 최소 동작·인터페이스를 분리하여 샘플 또는 집중 단위·특성화 테스트를 만들고 대표 성공·실패 입력을 실행합니다. 결과를 기록하고 실패를 보완한 뒤 검증된 단위 하나씩 넓은 코드로 확장합니다.

외부 라이브러리·SDK·API 연동은 다음을 수행합니다.

1. 버전, 필수 설정, 자격 증명·엔드포인트 전제, 프로젝트 빌드 대상을 기록합니다.
2. Debug로 빌드하여 의존성 로드·링크를 확인합니다.
3. 디버그 심볼·필요 로그를 켜고 실제 프로그램 또는 프로젝트 내부 최소 스모크 경로를 실행합니다.
4. 해당하는 초기화, 주요 호출, 반환 데이터·상태, 콜백, 타임아웃·취소, 오류 처리, 해제를 실행합니다.
5. 예외·어설션, 반환 코드·로그, 스레드·UI 스레드 규칙, 소유권, 종료를 확인합니다.
6. 외부 상태에 의존하면 잘못된 설정 또는 서비스 불가 경로를 최소 한 가지 검증합니다.
7. 재현 절차, 환경, 기대/실제 결과, 근거를 기록합니다.

컴파일·링크만으로 연동을 완료하지 않으며 실제 Debug 성공 또는 남은 위험을 포함한 문서화된 PM/사용자 예외가 필요합니다. 검토·보완 책임은 [개발 절차](delivery.ko.md#실행-절차)를 따릅니다.
