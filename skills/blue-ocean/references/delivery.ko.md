# 개발 진행과 인수

상대 명령·템플릿 경로는 설치된 블루오션 스킬 루트를 기준으로 합니다. 현재 작업에 해당하는 절만 읽습니다.

## 역할과 책임

실질적인 작업을 시작하기 전에 다음 역할을 정합니다.

- **프로젝트 매니저(PM):** 요청 결과, 범위, 완료 기준을 명확히 하고 브레인스토밍 아이템을 제시합니다. 각 분야의 아이디어를 취합하여 진행 방향을 결정하고, 로드맵 승인·업무 배정·최종 결과 보고를 담당합니다.
- **시스템 설계자:** PM 방향을 아키텍처, 인터페이스, 의존성, 마일스톤, 위험 요소, 검증 전략을 포함한 실행 가능한 로드맵으로 전환합니다. 승인된 스킬 카탈로그 또는 로컬에서 사용할 수 있는 스킬을 검색해 작업에 필요한 역량을 찾고, 최소한의 적합한 스킬을 선정하여 GUI 디자이너와 소프트웨어 개발자에게 배정합니다. 구현이 로드맵과 일치하는지 추적합니다.
- **GUI 디자이너:** 기존 화면, 컨트롤, 리소스, 상호작용 패턴을 조사하고 사용자 흐름, 화면 레이아웃, 컴포넌트 상태, 시각적 위계, 상호작용 규칙을 정의합니다. UI 변경 시 구현 전에 디자인 리뷰(DR) 시점에 사용자가 검토할 수 있는 간략한 UI 시안 이미지 또는 목업을 만들고, 제품의 기존 구조와 사용자 습관을 유지하는 범위에서 현대적인 시각 개선안을 제시합니다. 디자인 토큰·재사용 매핑·사용성·접근성 요구사항을 포함한 구현용 인수인계 자료를 만듭니다.
- **소프트웨어 개발자:** 요청된 언어로 승인된 작업을 구현하되, 적합한 기존 화면·컨트롤·헬퍼·라이브러리를 우선 적용합니다. 로직 변경은 작은 Sample Code 또는 최소 테스트로 의도한 동작을 먼저 입증한 후 대규모 수정으로 확장합니다. 외부 라이브러리·SDK·API를 사용하면 실제 Debug 실행으로 연동을 검증한 후 완료로 보고하며, 기존 아키텍처와 코딩 방식을 보존하고 실행 근거·필요한 차이·완료 내용·테스트·차단 요소를 보고합니다.
- **프로그램 검토 및 검증 QC:** 로드맵과 완료 기준을 기준으로 변경을 독립적으로 검토하고, 작업 규모에 맞는 검증을 수행하거나 요청합니다. 결함과 출시 위험을 기록합니다.
- **타이핑 전담 에이전트:** 다른 역할 에이전트가 승인 범위 안에서 구체적으로 지시한 내용만 작성·수정합니다. 반복 편집, 상용구 작성, 정해진 코드 규칙의 일괄 적용을 전문으로 합니다. 변경 내용과 확인 결과를 지시한 에이전트에게 돌려주며, 설계·로직 결정·승인은 담당 전문가와 PM이 책임집니다.

각 역할에 한 명의 책임 에이전트를 배정합니다. 자원이 부족할 때만 한 에이전트가 여러 역할을 겸할 수 있으며, 가능한 한 QC의 독립성을 유지합니다.
## 타이핑 전담 작업 지시

PM, 시스템 설계자, GUI 디자이너, 소프트웨어 개발자, QC는 승인된 로드맵 안에서 타이핑 전담에게 구체적인 작성·수정 작업을 지시할 수 있습니다. PM은 우선순위와 파일 담당을 조율하며, 작업 지시가 새 범위를 허용하거나 기존 설계 결정을 생략하는 근거가 되지는 않습니다.

- 지시에는 지시한 에이전트, 대상 파일·심볼, 정확한 변경 내용 또는 기계적으로 적용 가능한 변환 규칙, 적용할 코드 규칙과 예외(해당 프로젝트 로컬 규칙 ID·경로 포함), 필요한 경우 대표 예시, 완료 확인 방법을 포함합니다. 지시자는 편집을 넘기기 전에 동작·설계 선택을 해결합니다. 다른 역할이 지시하더라도 코드 정확성과 통합은 개발자가 책임집니다.
- 반복 선언·이벤트 연결, 승인된 코드·템플릿 확장, 서식 정리, 타입·범위 명명 규칙 적용, 지정된 문서 갱신을 맡깁니다. 기록된 프로젝트 명명표를 사용하고 공개 API·ABI, 생성 코드 등 승인된 예외를 보존합니다. 일괄 변경은 지정된 파일·심볼로 한정하며, 수정 대상이 아닌 레거시 코드까지 이름을 바꾸지 않습니다.
- 타이핑 전담은 전달받은 지시를 적용하며, 동작·아키텍처·의존성·UI 방향·추가 리팩터링을 임의로 결정하지 않습니다. 지시가 모호하거나 다른 지시·프로젝트 규칙과 충돌하거나 현재 소스에 맞지 않으면 해당 항목을 지시자에게 돌려보내고 필요한 최소한의 설명을 요청합니다. 독립적이고 명확한 항목은 계속 진행합니다.
- 같은 파일을 수정하는 지시는 순차 처리하고 편집 전 현재 내용을 다시 확인합니다. 기존 포매터·생성기 또는 범위가 제한된 스크립트로 지정된 반복 작업을 정확하게 처리할 수 있으면 활용하고, diff를 확인하며 지정된 검증을 실행합니다. 다른 에이전트의 변경을 덮어쓰지 않습니다.
- 작업 지시 참조, 변경 파일, 적용 규칙, 검증 근거, 미해결 항목을 반환합니다. 지시한 에이전트가 결과를 검토하고 개발자가 필요한 빌드·실행 검증을 수행하며, QC는 완료 기준을 독립적으로 검증합니다. QC가 수정 작업을 지시하더라도 최종 검증은 편집 에이전트와 분리합니다. 타이핑 전담은 자신의 결과를 승인하거나 기능을 최종 완료 처리하지 않습니다.
- 구현 규칙의 적용 가능성을 확인할 필요가 없으면 제품·설계 브레인스토밍에 타이핑 전담을 참여시키지 않으며, 기본 역할은 확정된 지시의 실행입니다. 슬롯이 부족하면 순차 배정하거나 겸임 사실을 알리고, 별도 에이전트가 실행된 것처럼 보고하지 않습니다.
## PM 주도 분야별 브레인스토밍

PM이 기능·문제·개선 아이템을 제시하면, 해당 로드맵의 방향을 확정하거나 구현을 배정하기 전에 브레인스토밍을 진행합니다. 판단의 규모에 맞춰 깊이를 조절하며, 방향이 이미 명확한 단순 변경은 역할별 짧은 의견으로 진행할 수 있습니다.

1. **PM의 아이템 공유:** 관련 역할 에이전트에게 동일한 간결한 설명을 전달합니다. 사용자에게 필요한 결과, 현재 동작과 참조 위치, 제약, 완료 기준, 아직 결정되지 않은 사항을 포함합니다. 먼저 아이디어를 요청하며 구현은 배정하지 않습니다. 기존 모델 배정과 저장된 스킬 선택 권한을 따릅니다.
2. **분야별 독립 아이디어 도출:** 각 참여 에이전트는 다른 에이전트의 제안을 보기 전에 자기 분야에서 아이디어를 도출하여 첫 제안에 편승하지 않도록 합니다. 사용 가능한 경우 자원 제한 안에서 별도 에이전트와 병렬 작업을 활용합니다. 한 에이전트가 여러 역할을 맡아야 하면 역할별 검토를 분리하고 독립 에이전트 검토가 아님을 알립니다. 관련 분야는 모두 참여시키며, 무관한 분야는 제외 이유를 짧게 기록합니다.

   - **시스템 설계자:** 아키텍처, 인터페이스, 데이터 흐름, 프로젝트·Mocha 재사용, 의존성 호환성, 단계별 제공 방안.
   - **GUI 디자이너:** 사용자 작업 흐름, 상호작용 대안, 시각적 위계, 기존 컨트롤·스타일, 접근성, UI가 영향을 받는 경우 DR용 간략한 시안.
   - **소프트웨어 개발자:** 구체적인 구현 대안, 재사용 코드, 구현 가능성, 작업량, 성능, 접근 방식을 확인할 최소 Sample Code 또는 Debug 검증.
   - **QC:** 실패 시나리오, 회귀, 테스트 가능성, 관찰 가능한 완료 검증, 남은 위험. 아이디어 단계에서는 실현 가능성을 검토하고, 이후 구현 결과는 독립적으로 검증합니다.

3. **비교 가능한 제안 제출:** 각 에이전트는 아이디어, 기대 효과, 근거·참조 위치, 장단점과 예상 작업량, 다른 역할에 대한 의존성, 검증 방법을 간결하게 제출합니다. 확인된 사실과 조사가 필요한 가정을 구분하고, 선택에 도움이 되면 더 단순한 대안도 포함합니다.
4. **PM 취합과 방향 결정:** PM은 제안을 모아 중복과 함께 적용할 수 있는 아이디어를 정리하고, 충돌을 드러냅니다. 모든 제안을 무조건 합치지 않습니다. 완료 기준, 사용자 가치, 기존 프로젝트 호환성·재사용, 작업량, 위험, 검증 비용으로 실행 가능한 방향을 비교합니다. 제약을 가장 잘 충족하는 최소한의 일관된 조합을 선택하고 선택 이유와 제외·보류한 아이디어의 이유를 기록합니다. 결정에 영향을 주는 구체적인 충돌이나 근거 부족만 관련 역할에 재검토시키며, 끝없는 토론을 진행하지 않습니다. 사용자가 확정한 요구사항을 우선하며, 중대한 제품 선택과 DR은 기존 사용자 결정 절차를 따릅니다.
5. **실행 계획으로 인계:** 기존 로드맵 또는 작업 플랜의 브레인스토밍 항목에 아이템 설명, 역할별 제안, 비교, 선택 방향, 남은 가정, 검증 담당을 저장합니다. 시스템 설계자는 PM 취합 결과를 담당자와 완료 검증이 있는 순차 작업으로 전환합니다. 해당 로드맵과 디자인 결정이 승인된 후 구현을 시작합니다. 요구사항 변경이나 검증 근거로 선택 방향이 유효하지 않게 되면 영향을 받는 아이디어를 재검토하고, 이후 세션에서도 참고할 수 있도록 결정 이력을 유지합니다.
## 운영 절차

여러 단계의 구현, 보완 반복, 세션을 넘기는 작업에는 이 문서의 실행 하네스를 함께 사용합니다. 기존 로드맵·DR·QC·권한 결정이 계속 기준입니다. 시작 전 업데이트·선택 권한은 [권한 절차](update-and-authority.ko.md), 외부 연동 Debug는 [구현 규칙](implementation.ko.md), 실제 UI 검증은 [GUI 절차](gui-workflow.ko.md)를 참조합니다.

1. PM은 [업데이트·권한 절차](update-and-authority.ko.md)에 따라 실행 초기 확인과 승인된 업데이트를 마친 뒤, 스킬 선택 권한을 읽거나 확인·저장하고 해당 프로젝트 로컬 작업 규칙을 불러와 요청을 간결한 목표, 제약, 완료 기준, 언어/플랫폼 결정으로 정리합니다. 구현 전에 범위에 중대한 영향을 주는 누락된 결정을 확인합니다. 제시한 아이템마다 분야별 브레인스토밍을 진행하고, 해당 로드맵을 확정하기 전에 PM이 방향을 취합합니다.
2. 신규 프로젝트에서는 시스템 설계자가 로드맵 승인 전에 공개 스킬 추천을 작성합니다. 결정된 플랫폼, 계획 기능, 제공 작업 흐름, 검증 요구사항에 맞춰 승인된 로컬 및 공개 스킬 카탈로그를 검색합니다. 최소한으로 유용한 후보만 추천하며, 스킬이 존재한다는 이유만으로 필요하다고 제시하거나 카탈로그 전체를 나열하지 않습니다. 각 후보는 출처, 목적, 대상 역할, 기대 효과, 사전 조건 또는 외부 서비스 접근, 의존성·개인정보·보안 영향, 프로젝트 호환성, 미설치 또는 로컬 스킬 대안을 포함하여 PM/사용자에게 제시합니다. 후보를 **이미 사용 가능**, **설치 추천**, **설치 비추천**으로 명확히 표시합니다. 각 스킬에 대한 사용자의 결정은 보류·거절을 포함해 기록합니다. 추천은 정보 제공일 뿐입니다. 사용자가 명시적으로 선택하고 외부 스킬 설치 절차를 통과하기 전에는 다운로드, 설치, 외부 서비스 연결 또는 사용 불가 스킬 배정을 하지 않습니다.
3. 시스템 설계자는 PM이 취합한 브레인스토밍 방향을 산출물, 순서, 담당자, 의존성, 기술 결정, 위험 요소, 검증 시점을 포함한 로드맵으로 전환합니다. 구현 배정 전에 기존 코드와 참조 자료를 조사하여 유사 화면, 컨트롤, 레이아웃 헬퍼, 스타일, 리소스, 함수, 데이터 흐름, 이미 참조 중인 라이브러리를 목록화합니다. 각 후보를 재사용·적응·교체로 구분하고 근거를 기록합니다. 전문 작업별로 승인된 스킬 카탈로그 또는 로컬 스킬을 검색하고, 선정한 스킬·대상 사용자·목적·사전 조건을 기록한 뒤 필요한 경우 GUI 디자이너 또는 소프트웨어 개발자에게 배정합니다. 신규 프로젝트에서는 공개 스킬 추천과 사용자 결정을 포함합니다. 사용자 대상 기능에는 디자인 리뷰(DR) 시점을 로드맵에 포함합니다. GUI 디자이너는 영향받는 화면·흐름의 간략한 이미지, 와이어프레임, 목업 또는 주석이 있는 기존 화면 시안을 제공하고, 사용자 검토·결정 결과를 수집한 뒤 구현 배정 전에 인수인계를 갱신합니다. 프로젝트에 지속 파일이 있으면 이 자료를 프로젝트 산출물에 보관하고, 그렇지 않으면 작업 응답에 제시합니다.
4. PM은 로드맵을 검토하고 범위 충돌을 해결하며 승인된 작업을 각 에이전트에게 배정합니다. 유용해 보인다는 이유만으로 범위 밖 구현을 시작하지 않습니다.
5. 구현 전에 GUI 디자이너와 소프트웨어 개발자는 각각 영향받는 구성요소 또는 화면, 기존 코드 참조, 구현 방식, 재사용 결정, 검증 방법을 포함한 작업 플랜을 작성합니다. UI 작업에서는 GUI 디자이너가 DR에서 간략한 시각 시안을 제시하고 피드백·미결정 사항·승인 결과를 기록하며, 해당 디자인 방향이 승인되거나 예외가 문서화되기 전에는 구현을 시작하지 않습니다. GUI 인수인계에는 현재 시각 기준, 현대화할 요소, 컴포넌트 상태, 간격·서체·색상 규칙, 상호작용, 접근성 고려사항, 각 요소에 적용할 프로젝트 고유 컨트롤 또는 헬퍼를 명시합니다. 로직 작업에서는 개발자가 전체 수정 전에 접근 방식을 입증할 최소 Sample Code, 입력·출력 또는 상태 검증, 테스트 명령을 먼저 정의합니다. 개발자는 각 디자인 요소를 가장 가까운 기존 구현 방식에 매핑하고, 안전한 매핑이 불가능하면 호환성 문제를 제기합니다. 시스템 설계자는 배정된 작업을 진행하기 전에 해당 플랜이 로드맵과 일치하는지 확인합니다.
6. 개발자는 배정된 항목을 구현하고 관련 빌드, 테스트, 검사를 실행합니다. 각 역할 에이전트는 구체적으로 확정된 반복 편집과 코드 규칙 적용을 위의 타이핑 전담 작업 지시로 전달합니다. 지시자가 반환된 diff를 검토하고 개발자는 통합 책임을 유지합니다. 로직 작업에서는 먼저 승인된 작은 Sample Code 또는 최소 테스트를 실행하고 결과를 확인한 뒤, 통과한 경우에만 단계적으로 수정 범위를 넓힙니다. 외부 라이브러리·SDK·API를 사용하면 아래 외부 연동 Debug 루틴을 따르며, 컴파일·링크 성공만으로 완료로 판단하지 않습니다. GUI 작업에서는 승인된 디자인 인수인계를 사용하고, 구현 가능성 문제나 디자인 차이가 있으면 임의 변경하지 말고 즉시 보고합니다. 계획된 각 GUI 검토 시점마다 GUI 디자이너는 현재 화면, 프로토타입 또는 구현 결과를 사용자에게 제시하고, 피드백과 확인 결과를 기록한 뒤 다음 영향을 받는 구현 단계 전에 인수인계 자료를 갱신합니다.
7. 시스템 설계자는 의미 있는 마일스톤마다 로드맵 정합성을 확인합니다. GUI 디자이너는 구현 화면이 승인된 상호작용 및 시각 요구사항과 일치하는지 검토합니다. QC는 중간 결과와 최종 변경 모두를 검토하고, 심각도와 재현 가능한 근거를 갖춘 결과를 기록하여 결함을 담당자에게 전달합니다.
8. QC 검증을 통과하지 못하면 실패한 기준, 근거, 담당자, 필요한 보완 내용을 기록합니다. 담당 GUI 디자이너 또는 개발자는 영향을 받은 결과를 보완·재작업하고 관련 검증을 다시 실행합니다. QC는 실패한 기준을 재검증하며, 통과하거나 PM/사용자가 남은 위험을 포함한 예외를 문서로 승인할 때까지 이 보완 과정을 반복합니다.
9. 구현과 관련 빌드·테스트가 끝나면 아래 Computer Use 검증 계획을 준비하고, 사용자에게 진행 여부를 확인한 뒤 승인된 실제 동작 테스트를 수행합니다. 실패는 QC 보완 과정으로 연결합니다.
10. 모든 필수 QC 검증이 통과했거나 승인된 예외가 기록된 후, PM은 원래 완료 기준에 대해 승인합니다. Computer Use 결과 또는 명확하게 기록된 생략·차단·해당 없음 상태를 포함합니다.
11. PM은 제공 범위, 변경 파일 또는 구성요소, 수행한 검증과 결과, 남은 위험 또는 후속 작업, 의도적인 차이를 포함한 최종 보고서를 작성합니다.
## 지속 실행 하네스

작업 상태 저장, 반복 가능한 검증, 중단 후 복구가 필요하면 [하네스 계약](harness.md)을 읽고 [설정 템플릿](../templates/harness-config.json)을 승인된 로드맵에 맞춥니다. Windows에서는 `scripts/harness.ps1`, 직접 실행 시 Python 3.10+로 `scripts/harness.py`를 사용합니다. 설정은 `cfg/blue-ocean.harness.json`, 상태·로그는 `cfg/blue-ocean.harness/`에 두며, `cfg/blue-ocean.preferences.json`과 기존 프로젝트 관례를 보존합니다. 단일 단계의 간단한 작업에는 상태 파일을 만들지 않아도 됩니다.

- PM/시스템 설계자는 담당자, 영향 입력 범위, 의존 작업, 관찰 가능한 완료 기준, 프로젝트 검증 명령, 근거 게이트, 실행 한도를 기록합니다. 관련 공유 코드·빌드·런타임 입력을 포함하고 생성 출력만 제외합니다. 기존 로드맵을 연결하고 같은 계획을 중복 관리하지 않습니다.
- 의존 작업과 필요한 DR/시작 게이트가 충족된 후 시작합니다. 개발자는 구현과 `verify` 실행, QC는 독립 검토와 근거를 담당합니다. 명령 통과 시 `verification_pending`이며, 현재 검증과 필수 QC/PM 근거를 확인한 `accept`만 `complete`로 전환합니다. 근거 파일이 있다는 사실만으로 내용의 타당성이나 사용자 승인을 입증하지 않습니다.
- 실패는 담당자에게 돌려보내 설정된 시도·시간 한도 안에서 보완·재검증합니다. 필수 환경 부재, 한도 소진, 미해결 결정은 차단 사유와 함께 PM에게 전달합니다. 재시도하려고 상태를 초기화하거나 예외를 꾸미지 않습니다. 기존 사용자 확인 기반 Computer Use와 런타임 검증 요구를 유지합니다.
- 중단·인계 시 상태, 로그, 차단 사유, 다음 행동을 남깁니다. 재개 시 실제 파일을 확인하고 `resume`으로 이전 결과를 점검한 뒤 사용합니다. 소스·설정·의존 작업·근거 변경 시 재검증합니다. `status`는 저장된 관찰 결과이며 새 정확성 검증이 아닙니다.
- 도우미는 로컬 상태·검증을 관리합니다. 에이전트 실행, 기능 구현, 권한 확대, 세션 자동 재시작, 기존 모델·자원 배정을 대신하지 않습니다. 배정은 블루오션 조율자가 맡고 독립 작업자가 공유 상태를 동시에 수정하지 않습니다.
