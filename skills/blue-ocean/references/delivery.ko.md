# 개발 진행

## 역할과 책임

본격적인 작업에는 다음 역할을 정합니다.

| 역할 | 책임 |
| --- | --- |
| 프로젝트 매니저(PM) | 범위·완료 기준, 브레인스토밍 설명·취합, 로드맵 승인, 배정, 통합, 최종 보고. [PM 관리](pm-control.ko.md)에 따라 예측·재계획 담당. |
| 시스템 설계자 | 아키텍처·인터페이스·의존성·로드맵, 기존 코드 조사, 지원 스킬 선택, 로드맵 정합성. |
| GUI 디자이너 | 기존 화면 조사, 시각·상호작용 설계, 사용자 검토, [GUI 절차](gui-workflow.ko.md)에 따른 구현 인계. |
| 소프트웨어 개발자 | [구현 규칙](implementation.ko.md)에 따른 재사용 중심 구현·통합·검증 근거. |
| QC | 독립 검토, 완료 기준 검증, 재현 가능한 결함 기록. |
| 타이핑 전담 | 구체적으로 확정된 반복 편집·코드 규칙 적용 후 지시자에게 검토 요청. |

역할별 책임자를 정합니다. 간단한 작업이나 자원 제한 시 역할을 겸할 수 있으나 수행 주체를 정확히 밝히고 가능한 경우 QC 독립성을 유지합니다. 배정에는 [모델·자원 규칙](agents-and-resources.ko.md)과 [PM 업무지시·보고 계약](pm-control.ko.md)을 적용합니다.

## 타이핑 전담 작업 지시

PM·시스템 설계자·GUI 디자이너·개발자·QC는 승인된 로드맵 안에서 작업을 지시할 수 있습니다. PM은 우선순위·파일 담당을 조율하고 개발자는 코드 정확성·통합 책임을 유지합니다.

- 지시자, 대상 파일·심볼, 정확한 변경 또는 결정적 변환 규칙, 적용 코드/로컬 규칙 ID와 예외, 필요한 경우 예시, 완료 검증을 명시합니다. 동작·설계 선택은 배정 전에 확정합니다.
- 반복 선언·이벤트 연결, 승인된 템플릿 확장, 서식, 명명 규칙, 지정 문서 수정에 사용합니다. 일괄 편집은 지정 파일·심볼로 제한하고 생성 코드·공개/ABI 결합·승인 예외를 보존합니다.
- 타이핑 전담은 동작·아키텍처·의존성·UI 방향·리팩터링을 임의 결정하지 않습니다. 모호하거나 충돌하는 항목은 지시자에게 돌려보내고 독립적인 명확한 항목은 계속합니다. 브레인스토밍 참여는 구현 규칙의 실행 가능성 확인으로 제한합니다.
- 공유 파일 지시는 순차 처리하고 현재 내용을 다시 확인합니다. 적합한 기존 포매터·생성기를 활용하고 diff와 지정 검증을 확인합니다.
- 지시 참조, 변경 파일, 적용 규칙, 결과, 미해결 사항을 반환합니다. 지시자는 diff를 검토하고 개발자는 통합 검증을 수행합니다. QC가 보완을 지시한 경우에도 최종 검증은 편집자와 분리합니다. 타이핑 전담은 기능을 자체 인수하지 않습니다.

## PM 주도 분야별 브레인스토밍

기능·문제·개선 방향을 확정하기 전에 분야별 아이디어를 모읍니다. 요구사항이 확정된 통상 수정은 짧은 역할별 의견으로 진행할 수 있습니다.

1. **작업 설명:** PM이 목표, 현재 동작·참조 위치, 제약, 완료 기준, 열린 결정을 공유하고 구현 전에 아이디어를 요청합니다.
2. **독립 제안:** 관련 전문가는 먼저 독립적으로 검토합니다. 설계자는 아키텍처·재사용·의존성, GUI는 작업 흐름·시각·접근성과 DR 시안, 개발자는 실행 가능성·작업량·성능과 대표 샘플, QC는 실패·회귀·검증 가능성을 다룹니다. 무관한 분야는 이유와 함께 생략합니다. 자원 한도 안에서 별도 에이전트가 병렬 진행할 수 있으며, 겸임 의견을 독립 검토로 표현하지 않습니다.
3. **비교:** 각 제안은 아이디어, 효과, 근거, 장단점·작업량, 의존성, 검증 방법을 포함하고 사실·가정을 구분합니다. PM은 완료 기준·사용자 가치·호환성·재사용·작업량·위험·검증 비용으로 비교하여 호환 제안을 합치고 충돌·제외·보류 사유를 기록합니다. 결정에 영향을 주는 부족한 부분만 보완합니다.
4. **인계:** 기존 로드맵·작업 플랜에 설명, 제안, 선택 방향, 가정, 검증 담당을 남깁니다. 시스템 설계자는 이를 순차 작업으로 전환합니다. 사용자 확정 요구와 해당 사용자 결정을 유지하며 요구·근거가 달라지면 영향받는 선택을 재검토합니다.

## 실행 절차

1. **범위 정리:** [시작·권한 절차](update-and-authority.ko.md)와 [로컬 규칙](../localrule/local-skills.md)을 적용합니다. 목표·제약·완료 기준·언어/플랫폼을 정하고 중요한 미결정 사항과 해당 브레인스토밍을 마무리합니다.
2. **계획:** 유사 화면·컨트롤·헬퍼·스타일/리소스·심볼·데이터 흐름·참조 라이브러리를 조사하고 재사용·적응·교체 판단의 근거를 기록합니다. 산출물, 순서, 담당자, 의존성, 위험, 검증을 정합니다. 저장된 권한 안에서 사용 가능한 지원 스킬을 배정하고 대상 역할·목적·사전 조건을 기록합니다.
3. **신규 프로젝트 스킬 추천:** 로드맵 승인 전에 승인된 로컬·공개 카탈로그에서 최소한의 유용한 스킬을 추천합니다. 출처, 목적·역할, 효과, 사전 조건·접근 권한, 의존성·개인정보·보안 영향, 호환성, 로컬/미설치 대안을 제시합니다. 사용 가능·설치 추천·추천하지 않음으로 표시하고 사용자 허용·거절·보류를 기록합니다. 미설치 역량은 [외부 설치 절차](update-and-authority.ko.md)를 따르며 추천만으로 다운로드·연결하지 않습니다.
4. **승인·배정:** PM은 로드맵을 승인하고 [PM 관리](pm-control.ko.md)에 따라 범위가 정해진 지시·과거 기반 예상·할당량·보고·예측을 관리합니다. GUI 디자이너·개발자는 영향 구성요소, 기존 참조, 구현 방식, 재사용, 검증이 포함된 플랜을 준비하고 설계자는 정합성을 확인합니다. UI는 구현 전에 [사용자 컨펌을 받은 시안 인계](gui-workflow.ko.md#구현-전-ui-시안과-사용자-컨펌)가 필요합니다.
5. **구현:** 개발자는 [재사용·명명·샘플·Debug 규칙](implementation.ko.md)을 따르고 반복 편집은 위의 구체적인 작업 지시를 활용합니다. 승인된 GUI 인계를 사용하고 실행 가능성 문제를 보고하며 다음 영향 단계 전에 [GUI 검토 시점](gui-workflow.ko.md#디자인-인계와-검토)을 적용합니다.
6. **검토·보완:** 설계자는 로드맵, GUI 디자이너는 승인 디자인, QC는 중간·최종 결과를 확인합니다. 결함과 제안을 구분하고 차단 결함에는 기준, 심각도, 기대/실제 결과, 재현·근거, 담당자를 기록합니다. 범위 안에서 수정·영향 검증 후 QC가 재검증하거나, 남은 위험을 포함한 PM/사용자 예외 승인을 기록합니다.
7. **검증·인수:** 구현·빌드 검증 후 해당하는 [Computer Use 계획](gui-workflow.ko.md#사용자-확인-후-computer-use-실제-동작-검증)을 준비하여 허용 범위에서 실행합니다. 생략·차단·해당 없음을 명시합니다. 필수 QC 근거나 허용된 예외를 확인한 뒤 PM이 원래 완료 기준으로 인수합니다.
8. **종료:** 범위, 변경 파일·구성요소, 검증·결과, 차이, 남은 위험·후속 작업을 보고하고 [PM 관리](pm-control.ko.md)에 따라 예상·실제 이력을 마감합니다.

## 지속 실행 하네스

다단계 실행·보완 반복·세션 간 작업은 [하네스 계약](harness.md)과 [설정 템플릿](../templates/harness-config.json)을 적용합니다. 설정·명령·게이트·한도·복구 상세는 해당 문서를 따르고 로드맵은 중복 작성하지 않고 연결합니다. 단순한 한 단계 작업에는 새 원장이 필요하지 않습니다. 기존 선택·상태를 보존하고 중단·저장 결과를 신뢰하기 전에 `resume`을 수행합니다.
