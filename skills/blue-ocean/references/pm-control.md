# PM work control, forecasts and reporting

Read before assigning work or reporting progress, remaining effort, token use or completion time. Apply to PM work and every subagent, including specialist-issued typing orders. For a small task, keep the same facts in a brief task record; do not create agents or a ledger merely to fill a report.

## PM authority and work orders

- Within approved scope and user limits, the PM sets priorities, owners, dependencies, concurrency, reporting checkpoints and task token allowances; requests evidence; and pauses, cancels, reassigns or replans redundant, stalled or over-budget work. Preserve completed artifacts and explain material forecast changes. Specialist instructions and nested agents must roll up to the PM before additional work begins; they cannot bypass the plan or create an untracked budget.
- This management authority does not change saved skill-selection authority, permit new paid services, increase a user token cap, expand product scope, waive required QC/DR/runtime evidence, or override an explicit stop. Continue independent authorized work while a separate decision is pending. Do not request fresh permission for routine scheduling inside existing authorization.
- Before dispatch, record task ID, parent task, issuing agent, agent ID/role/effective model, scope and exclusions, deliverables, dependencies, file ownership, acceptance evidence/owner, weighted milestones (including validation and acceptance), token estimate, remaining duration/finish window, reporting cadence and escalation conditions. Include PM integration, review and QC effort in the plan. Identify historical comparison records, assumptions and confidence. Share this concrete brief with the worker; get an acknowledgement or corrected estimate at its first reporting opportunity.
- Separate the initial estimate, current forecast and task allowance. An estimate is a range, not permission to consume its upper bound. Allocate an allowance only inside an existing project/user limit or an explicitly recorded PM planning allowance; label the latter as a planning threshold rather than a user-approved quota. Never invent a user limit. A worker returns results before starting unplanned extensions or passing its allowance; the PM chooses the next authorized step.

## Reports and progress evidence

- Workers report at acknowledgement, completed milestone, handoff, blocker, material forecast change and completion. During active multi-agent work use a default reporting target of 60 seconds, adjustable by the PM for the task. Report at the next available tool/message boundary; this is not a background timer or a guarantee that a blocked client/tool can emit live updates. Do not interrupt a healthy long operation solely to obtain a percentage.
- Every report contains task/agent ID, timestamp with timezone, state, completed milestones and evidence, current activity, remaining deliverables/checks, progress, tokens used with measurement status/source/coverage, remaining token range, remaining duration and finish window, blockers/dependencies, confidence and next action/checkpoint. For unchanged long operations, report the last observation and its age. A heartbeat proves liveness, not progress.
- Derive progress from completed, evidenced milestones with agreed weights summing to 1. Include nonzero weights for required integration, verification and acceptance. Do not infer progress from elapsed time, tokens spent, file count or the agent saying “almost done.” Implementation finished is distinct from accepted completion; only current required evidence and PM acceptance permit task status `complete` and 100%.
- Overall progress is the sum of task progress multiplied by agreed scope weights, with each leaf deliverable counted once. Parent summaries do not add another copy of child work. Preserve baseline weights across forecast updates; record a scope/weight revision or a reopened milestone, including any decrease in progress. Show execution status separately from progress (`pending`, `running`, `verification_pending`, `needs_changes`, `blocked`, `complete`, `cancelled`). A reporting timeout is `stale`, not automatic failure or completion.
- The PM requests an update at the first missed checkpoint and checks the actual agent/tool state before interrupting, restarting or reallocating. Escalate immediately on blockers, a forecast outside its prior range, threatened allowance/user limit, changed dependencies or missing acceptance evidence. If no response can be collected, preserve the last report, mark freshness/ETA uncertain and continue independent work; never manufacture fresh worker reports.
- Required report fields may be unknown: use `null`/`unknown` with the reason and next information-gathering step. If an inherited task has no agreed milestone weights or completion evidence, show its observed state and uncomputed progress until the PM establishes a grounded baseline; do not invent a percentage to complete the table.

## Historical token estimates and calibration

1. Before dispatch, search existing task/history records for comparable completed work. Match task type, deliverables/work units, codebase/context size, reuse, model, implementation complexity, dependencies, validation and correction loops. Start with the same project, then use permitted cross-project summaries without copying confidential content. Record record IDs/paths, sample count, measurement coverage and why comparisons fit or differ. An empty history is explicitly a low-confidence initial estimate, never a fabricated historical average.
2. Prefer measured end-to-end token totals from comparable runs. Use a median tokens-per-comparable-work-unit baseline and the observed spread to estimate a low/high range, adjusting for documented differences such as context loading, unfamiliar code, model or extra QC. Do not compare unrelated work by line count or elapsed time alone. A small or mismatched sample needs a wider range and lower confidence; explain any judgment-based range. One record is an analogy, not a reliable statistical interval. Keep measured and estimated samples distinguishable; do not pool them as measured evidence.

   When history is absent, break the assignment into concrete discovery/context, implementation and validation/handoff work; estimate coarse ranges for those slices from known work units and stated assumptions. Label these judgment estimates low confidence, and revise after the first bounded milestone. If even that basis is unavailable, leave the affected forecast unknown with a reason and a bounded next investigation; do not supply arbitrary precision. Confirm what historical “verified” work included before adding separate QC/PM costs, so prior validation is not counted twice.
3. Estimate each disjoint cost owner: PM planning/orchestration, each worker (including input/context), integration, QC, expected correction work and an explicit project contingency. Parent task totals roll up child costs, excluding parent summary duplicates. Never add child usage again if a provider's parent-session total already includes it. State whether the forecast covers input/output, cached input and reasoning; cached input may be a subset of input and reasoning may be a subset of output. Follow the observed provider accounting, count each token once and retain the source counters. Do not infer money from tokens or convert time into purported actual tokens.
4. Record actual tokens only when exposed by a tool/session/provider counter, with timestamp, source and coverage (agent/task/session, cumulative or delta). Use deltas only for the matching measured interval and preserve earlier attempt/retry costs; record counter resets and coverage gaps. Missing usage is `null`/`unavailable`, not zero. Keep reported actuals and estimated consumption separate. With partial telemetry, show the measured subtotal and missing coverage rather than calling it the project actual total. Do not claim hidden context, token balances, hard budget enforcement or live billing is observable.
5. Update remaining tokens from the work still required and comparable evidence; consumption is not progress. With complete nonoverlapping telemetry, `forecast_total = measured_used + estimated_remaining`; otherwise show the measured subtotal, estimated unmeasured consumption and estimated remaining separately, labelling their sum a forecast. Keep the original estimate and every revision with timestamp/reason. Track reserve separately; release it only when its risk is resolved, rather than silently counting it both in tasks and contingency. A forecast approaching/exceeding the task allowance or user cap requires a PM decision before the next discretionary dispatch. Unknown consumption cannot establish that a hard cap remains safe; report that limitation and stop dependent discretionary dispatch when cap compliance cannot be established.
6. At closure (including failed/cancelled attempts), preserve the original/current estimates, actual measured usage or explicit unavailability, model, actual work units, context/reuse characteristics, validation/correction count, elapsed active/wait time, outcome and estimate error with explanation. Compare actual/original midpoint and actual/current midpoint only for matching measured coverage. Use comparable completed records to calibrate subsequent estimates; retain failed/cancelled costs as risk/rework evidence rather than successful-unit baselines. Never overwrite prior observations with a later estimate.

## Remaining time and project finish

- Estimate remaining active work and verification from comparable durations and observed milestones; report a range and confidence. Record waiting separately (dependency, agent slot, build, user decision, unavailable environment). Do not use a universal tokens-per-minute conversion or linear elapsed/progress extrapolation as a promised finish.
- Compute the finish window along the remaining dependency path, respecting actual agent slots, shared-file serialization, integration, QC and correction allowance. Sum sequential steps; independent tasks can overlap only when resources permit. Project time is not the sum of all worker times or the shortest worker ETA.
- Show “remaining 20–35 minutes; expected finish 15:20–15:35 Asia/Seoul,” for example, with the observation timestamp and assumptions. Use the user's timezone. When an external wait has no known end, show “finish unknown; 20–35 minutes of active work after dependency X resolves,” and the next checkpoint. A stale or interrupted run needs a fresh report/reconciliation before its old finish window can be reused. Do not claim monitoring continues after the turn ends.

## Persistent record and user-facing view

Reuse the existing roadmap/task record. For multi-step or cross-session work with no equivalent record, adapt [the task-record template](../templates/pm-task-record.json) into `cfg/blue-ocean.harness/pm/tasks/<task-id>.json`. This is a PM-maintained reporting contract, not a new executable command or an automatically enforced schema. The harness `state.json` continues to own verification/acceptance state; link it and reconcile discrepancies before reporting. One PM writer persists reports serially through a temporary file and replace, reads back writes, and retains prior reports/revisions/closed records. Workers send updates instead of concurrently editing the shared record. Invalid existing data must be preserved and reconciled, never reset. Keep project records across shared skill updates; do not save project history in reusable skill templates or commit local logs by default.

At dispatch, meaningful checkpoints, a status request and closure, the PM provides a compact Korean view:

| Task / agent (role, model) | State / progress / observed at | Completed / remaining | Used tokens (measured or estimated) / remaining range / allowance | Remaining time / finish window | Blocker / next action |
| --- | --- | --- | --- | --- | --- |

Below it, show overall evidence-based progress, remaining deliverables and acceptance, measured coverage and total token forecast versus original estimate/limit, historical basis/confidence, project finish window/timezone/assumptions, and the next checkpoint. Mark stale rows clearly. A short task may use one sentence with these relevant facts. At closure report estimate-versus-actual differences and the saved history reference; do not label a forecast as actual usage or acceptance.
