# 블루오션

승인된 목표를 작업 규모에 맞는 계획, 재사용, 검증 근거로 완수합니다. 기존 프로젝트 관례와 사용자의 명시적 선택을 보존합니다. 별도 요청이 없으면 계획·진행·결과는 한글로 작성하고 코드·식별자는 유지합니다.

## 시작과 공통 제약

- 실행 초기에 [업데이트와 권한](references/update-and-authority.ko.md)을 읽고 지정 GitHub 소스를 한 번 확인합니다. 원격 업데이트와 로컬 변경·로컬 선행 이력을 구분하고 더 최신인 로컬 기능을 보존합니다. 명시적으로 요청한 업데이트는 검토된 범위에서 같은 허락을 반복해서 묻지 않고 진행하며, 그 외에는 설치본 교체 전에 필요한 결정을 받습니다. 복구 가능한 백업과 후보 검증을 수행합니다.
- 지원 스킬 선택 전에 동일한 프로젝트 루트의 `cfg/blue-ocean.preferences.json`을 읽습니다. 저장된 `user`/`pm` 권한과 스킬별 allow/deny/defer를 따릅니다. 저장되거나 명시된 선택이 없으면 의존 작업 전에 선택을 받고, 저장 성공이나 추가 접근 권한을 가정하지 않습니다. 저장·외부 설치 상세는 권한 문서를 따릅니다.
- 프로젝트 분석·구현 시 `project-symbol-guide`(프로젝트 심볼 가이드)가 설치되어 있으면 기존 변수·함수 검색과 재사용, 소스 근거가 연결된 카탈로그 유지에 적극 사용합니다. 이 지속 사용자 지시로 해당 스킬 사용은 이미 허용되었으므로 선택 자체를 다시 묻지 않습니다. 이후 사용자 제한과 [심볼 가이드 절차](references/implementation.ko.md#프로젝트-심볼-가이드)를 따르며 일반적인 스킬 선택 권한까지 확대하지 않습니다.
- 계획 전에 관련 프로젝트 로컬 규칙을 읽습니다. 명확한 지속 지시와 실제 반복 교정은 [로컬 스킬 절차](references/local-skills.md)에 따라 범위·근거·저장 중지·작업 예외와 함께 관리합니다. [로컬 템플릿](templates/local-skill/SKILL.md)과 [레지스트리](templates/local-skill/references/rules.json)를 재사용하고 매뉴얼·로그를 사용자 지시로 승격하지 않습니다.
- 모든 블루오션 역할은 **GPT-6.1 Sol** (`gpt-6.1-sol`)을 사용합니다. 에이전트 생성이나 큰 병렬 작업 전에 [에이전트와 자원](references/agents-and-resources.ko.md)을 읽습니다. 모델 가용성을 확인하며 임의 대체하지 않습니다. 독립 작업만 병렬화하고 같은 파일 편집은 순차 진행하며 가능한 경우 독립 QC를 유지합니다. 간단한 작업은 역할을 겸할 수 있으나 수행 주체를 정확하게 보고합니다.
- 불필요한 작업 생략, 프로젝트 기존 코드, 언어 표준 라이브러리, 플랫폼 기본 기능, 설치된 의존성, 최소 구현 순으로 충분한 첫 해법을 선택합니다. 필수 검증·오류/데이터 손실 처리·보안·접근성·관측성·테스트를 보존하고 새 변수 전에 호환되는 기존 값을 확인합니다.
- 승인된 로드맵·DR·실제 구동·QC 절차를 보존합니다. 증거 파일·명령 성공·캐시 요약만으로 완료나 사용자 승인을 입증하지 않습니다. 중요한 결정에 막힌 단계가 있어도 독립적인 승인 작업은 계속합니다.

## 해당 작업의 문서 선택

아래 문서는 조건별 연결이며 시작할 때 전부 읽는 목록이 아닙니다. 해당 결정 전에 필요한 절을 읽습니다. 요구사항이 확정된 통상적인 수정은 짧은 작업 기록과 관련 검증으로 진행할 수 있으며, 무관한 역할·전체 저장소 조사·새 원장은 필요하지 않습니다. 작업 규모에 맞춘 적용으로 해당 DR, 외부 연동 Debug, Computer Use 확인 또는 독립 인수 조건을 없애지는 않습니다.

| 현재 작업 | 읽고 적용할 문서 |
| --- | --- |
| 본격 구현·아키텍처·기능 선택·전문가 인계 | [개발 진행](references/delivery.ko.md): 역할, PM 취합, 작업 계획, 소유권, 인수. |
| 소스 변경·C++/MFC 재사용·새 의존성 | [구현](references/implementation.ko.md): 새 구현 선택 전 Mocha 검색, 명명 규칙, 기존 빌드, 라이브러리 영향, Debug 연동, QC. 다이어그램·문서도 영향 영역만 확인합니다. |
| UI 배치·컨트롤·상호작용·최종 실제 UI 검증 | [GUI 절차](references/gui-workflow.ko.md): 구현 전 시각 제안과 사용자 방향, WPF 디자이너/MFC DC 기본값, 구체적인 Computer Use 계획과 명시적 실행 범위. |
| 다단계 실행·보완 반복·세션 복구 | [하네스](references/harness.md)와 [설정 템플릿](templates/harness-config.json). 상태는 `cfg/blue-ocean.harness/`에 유지하고 중단 후 `resume`으로 변경 입력을 재검증합니다. 명령 통과는 `verification_pending`이며 인수에는 현재 QC/PM 근거가 필요합니다. |

| Windows/WSL 체크아웃·병렬 빌드 준비·모델/속도 설정·도구 연동 변경 | [실행 환경](references/execution-environment.ko.md): 실제 체크아웃, 빌드 경로, 도구 가용성, 복구 확인. |
| 이 스킬·문서 선택 기준·모델·도구 업데이트 | [스킬 평가](references/skill-evaluation.ko.md)와 [사례](templates/skill-evaluation-cases.json): 구조 검사와 대상 클라이언트의 대표 결정 검증. |
| 명시적으로 요청한 코드 정리·CI 유지보수 | [실행 환경](references/execution-environment.ko.md)의 유지보수 절: 삭제 근거와 영향 검증. |

## 완료

개발자는 변경에 맞는 프로젝트 고유 검증을 수행하며 외부 라이브러리·SDK·API에는 실제 Debug 구동 근거가 필요합니다. QC는 관측한 기대/실제 결과를 기록하고 보완 후 재검증합니다. 실행 가능한 빌드와 구체적인 실제 UI 시나리오를 준비한 뒤 Computer Use 실행 확인을 받으며 같은 범위의 명시적 승인은 재사용합니다. 불가·거절된 검증은 차단/미실행으로 기록하고 통과로 표시하지 않습니다. PM은 필수 근거나 권한 있는 문서화된 예외를 확인한 뒤 인수하고 제공 범위·변경 파일·검증·남은 제약을 보고합니다.
