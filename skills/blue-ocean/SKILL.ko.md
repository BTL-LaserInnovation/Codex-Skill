# 블루오션

이 스킬은 명확한 멀티 에이전트 개발 절차가 필요한 소프트웨어 개발 작업에 사용합니다. C++, C# 및 사용자가 요청한 다른 플랫폼을 지원하며, 특정 프레임워크를 강제하거나 사용자의 제품 요구사항을 변경하지 않습니다.

## 역할과 책임

실질적인 작업을 시작하기 전에 다음 역할을 정합니다.

- **프로젝트 매니저(PM):** 요청 결과, 범위, 완료 기준을 명확히 하고 진행 방향을 결정합니다. 로드맵을 승인하고 업무를 배정하며 최종 결과를 보고합니다.
- **시스템 설계자:** PM 방향을 아키텍처, 인터페이스, 의존성, 마일스톤, 위험 요소, 검증 전략을 포함한 실행 가능한 로드맵으로 전환합니다. 승인된 스킬 카탈로그 또는 로컬에서 사용할 수 있는 스킬을 검색해 작업에 필요한 역량을 찾고, 최소한의 적합한 스킬을 선정하여 GUI 디자이너와 소프트웨어 개발자에게 배정합니다. 구현이 로드맵과 일치하는지 추적합니다.
- **GUI 디자이너:** 기존 화면, 컨트롤, 리소스, 상호작용 패턴을 조사하고 사용자 흐름, 화면 레이아웃, 컴포넌트 상태, 시각적 위계, 상호작용 규칙을 정의합니다. UI 변경 시 구현 전에 디자인 리뷰(DR) 시점에 사용자가 검토할 수 있는 간략한 UI 시안 이미지 또는 목업을 만들고, 제품의 기존 구조와 사용자 습관을 유지하는 범위에서 현대적인 시각 개선안을 제시합니다. 디자인 토큰·재사용 매핑·사용성·접근성 요구사항을 포함한 구현용 인수인계 자료를 만듭니다.
- **소프트웨어 개발자:** 요청된 언어로 승인된 작업을 구현하되, 적합한 기존 화면·컨트롤·헬퍼·라이브러리를 우선 적용합니다. 로직 변경은 작은 Sample Code 또는 최소 테스트로 의도한 동작을 먼저 입증한 후 대규모 수정으로 확장합니다. 외부 라이브러리·SDK·API를 사용하면 실제 Debug 실행으로 연동을 검증한 후 완료로 보고하며, 기존 아키텍처와 코딩 방식을 보존하고 실행 근거·필요한 차이·완료 내용·테스트·차단 요소를 보고합니다.
- **프로그램 검토 및 검증 QC:** 로드맵과 완료 기준을 기준으로 변경을 독립적으로 검토하고, 작업 규모에 맞는 검증을 수행하거나 요청합니다. 결함과 출시 위험을 기록합니다.

각 역할에 한 명의 책임 에이전트를 배정합니다. 자원이 부족할 때만 한 에이전트가 여러 역할을 겸할 수 있으며, 가능한 한 QC의 독립성을 유지합니다.

## 운영 절차

1. PM은 요청을 간결한 목표, 제약, 완료 기준, 언어/플랫폼 결정으로 정리합니다. 구현 전에 범위에 중대한 영향을 주는 누락된 결정을 확인합니다.
2. 시스템 설계자는 산출물, 순서, 담당자, 의존성, 기술 결정, 위험 요소, 검증 시점을 포함한 로드맵을 작성합니다. 구현 배정 전에 기존 코드와 참조 자료를 조사하여 유사 화면, 컨트롤, 레이아웃 헬퍼, 스타일, 리소스, 함수, 데이터 흐름, 이미 참조 중인 라이브러리를 목록화합니다. 각 후보를 재사용·적응·교체로 구분하고 근거를 기록합니다. 전문 작업별로 승인된 스킬 카탈로그 또는 로컬 스킬을 검색하고, 선정한 스킬·대상 사용자·목적·사전 조건을 기록한 뒤 필요한 경우 GUI 디자이너 또는 소프트웨어 개발자에게 배정합니다. 사용자 대상 기능에는 디자인 리뷰(DR) 시점을 로드맵에 포함합니다. GUI 디자이너는 영향받는 화면·흐름의 간략한 이미지, 와이어프레임, 목업 또는 주석이 있는 기존 화면 시안을 제공하고, 사용자 검토·결정 결과를 수집한 뒤 구현 배정 전에 인수인계를 갱신합니다. 프로젝트에 지속 파일이 있으면 이 자료를 프로젝트 산출물에 보관하고, 그렇지 않으면 작업 응답에 제시합니다.
3. PM은 로드맵을 검토하고 범위 충돌을 해결하며 승인된 작업을 각 에이전트에게 배정합니다. 유용해 보인다는 이유만으로 범위 밖 구현을 시작하지 않습니다.
4. 구현 전에 GUI 디자이너와 소프트웨어 개발자는 각각 영향받는 구성요소 또는 화면, 기존 코드 참조, 구현 방식, 재사용 결정, 검증 방법을 포함한 작업 플랜을 작성합니다. UI 작업에서는 GUI 디자이너가 DR에서 간략한 시각 시안을 제시하고 피드백·미결정 사항·승인 결과를 기록하며, 해당 디자인 방향이 승인되거나 예외가 문서화되기 전에는 구현을 시작하지 않습니다. GUI 인수인계에는 현재 시각 기준, 현대화할 요소, 컴포넌트 상태, 간격·서체·색상 규칙, 상호작용, 접근성 고려사항, 각 요소에 적용할 프로젝트 고유 컨트롤 또는 헬퍼를 명시합니다. 로직 작업에서는 개발자가 전체 수정 전에 접근 방식을 입증할 최소 Sample Code, 입력·출력 또는 상태 검증, 테스트 명령을 먼저 정의합니다. 개발자는 각 디자인 요소를 가장 가까운 기존 구현 방식에 매핑하고, 안전한 매핑이 불가능하면 호환성 문제를 제기합니다. 시스템 설계자는 배정된 작업을 진행하기 전에 해당 플랜이 로드맵과 일치하는지 확인합니다.
5. 개발자는 배정된 항목을 구현하고 관련 빌드, 테스트, 검사를 실행합니다. 로직 작업에서는 먼저 승인된 작은 Sample Code 또는 최소 테스트를 실행하고 결과를 확인한 뒤, 통과한 경우에만 단계적으로 수정 범위를 넓힙니다. 외부 라이브러리·SDK·API를 사용하면 아래 외부 연동 Debug 루틴을 따르며, 컴파일·링크 성공만으로 완료로 판단하지 않습니다. GUI 작업에서는 승인된 디자인 인수인계를 사용하고, 구현 가능성 문제나 디자인 차이가 있으면 임의 변경하지 말고 즉시 보고합니다. 계획된 각 GUI 검토 시점마다 GUI 디자이너는 현재 화면, 프로토타입 또는 구현 결과를 사용자에게 제시하고, 피드백과 확인 결과를 기록한 뒤 다음 영향을 받는 구현 단계 전에 인수인계 자료를 갱신합니다.
6. 시스템 설계자는 의미 있는 마일스톤마다 로드맵 정합성을 확인합니다. GUI 디자이너는 구현 화면이 승인된 상호작용 및 시각 요구사항과 일치하는지 검토합니다. QC는 중간 결과와 최종 변경 모두를 검토하고, 심각도와 재현 가능한 근거를 갖춘 결과를 기록하여 결함을 담당자에게 전달합니다.
7. QC 검증을 통과하지 못하면 실패한 기준, 근거, 담당자, 필요한 보완 내용을 기록합니다. 담당 GUI 디자이너 또는 개발자는 영향을 받은 결과를 보완·재작업하고 관련 검증을 다시 실행합니다. QC는 실패한 기준을 재검증하며, 통과하거나 PM/사용자가 남은 위험을 포함한 예외를 문서로 승인할 때까지 이 보완 과정을 반복합니다.
8. 모든 필수 QC 검증이 통과했거나 승인된 예외가 기록된 후, PM은 원래 완료 기준에 대해 승인합니다.
9. PM은 제공 범위, 변경 파일 또는 구성요소, 수행한 검증과 결과, 남은 위험 또는 후속 작업, 의도적인 차이를 포함한 최종 보고서를 작성합니다.

## 협업 규칙

- 독립적인 작업에만 병렬 작업을 사용합니다. 아키텍처 결정과 공유 파일 편집은 충돌을 피하도록 순차적으로 진행합니다.
- 승인된 로드맵을 기준 문서로 취급합니다. PM이 중요한 범위, 설계, 일정 변경을 승인하면 로드맵을 갱신합니다.
- 시스템 설계자는 이미 사용할 수 있고 프로젝트와 관련된 스킬을 GUI 디자이너 또는 소프트웨어 개발자에게 배정할 수 있습니다. 배정은 지정된 작업에서 스킬을 사용할 권한만 부여하며, 외부 서비스 접근, 새 자격 증명, 의존성 설치 권한을 부여하지 않습니다.
- 시스템 설계자는 배정된 GUI 디자이너와 소프트웨어 개발자에게 적절한 사용 도구를 제공합니다. 여기에는 관련 스킬, 프로젝트 기본 빌드·테스트 명령, 디자인 시스템 자료, 적용할 기존 코드의 위치가 포함됩니다. 단, 외부 서비스, 자격 증명, 새 의존성에 필요한 승인을 우회할 수는 없습니다.
- 코딩 개발 작업에서는 시스템 설계자가 Superpowers 스킬의 사용 가능 여부를 확인하고, 해당 작업 흐름이 적합하면 소프트웨어 개발자에게 배정할 수 있습니다. Superpowers는 보조 참조로 사용하며, 승인된 로드맵·프로젝트 관례·완료 기준이 최우선입니다. Superpowers를 사용할 수 없다고 해서 설치가 자동으로 허용되는 것은 아니며, 이 경우 프로젝트의 기존 도구와 작업 방식을 따릅니다.
- 시스템 설계자는 구현 지침을 배정하기 전에 기존 코드베이스에서 유사한 화면, 구성요소, 함수, 변수, 데이터 흐름을 검색하고, 담당 에이전트에게 참고할 내용을 추천합니다.
- 작업 지시자가 참고 코드 또는 참고 프로젝트를 알려 주면 그 구조와 함수가 사용되는 과정을 확인하고, 그 근거를 구현 플랜과 호환성 지침에 반영합니다.
- GUI 현대화는 현재 제품과 참조 자료에서 시각적·동작 기준을 먼저 확립한 후 진행합니다. 필요에 따라 위계, 간격, 서체, 색상, 피드백, 빈 상태·로딩 상태·오류 상태, 접근성을 개선하되, PM이 동작 변경을 명시적으로 승인하지 않는 한 기존 탐색 방식, 도메인 용어, 핵심 작업 흐름, 플랫폼 관례를 보존합니다.
- UI 작업은 구현 전 이미지 기반 DR 게이트를 사용합니다. 영향받는 화면·흐름만 간략한 와이어프레임, 목업, 주석 화면 또는 유사 시안으로 제시하고 사용자 피드백과 진행 방향을 기록한 뒤 인수인계를 갱신합니다. 상호작용·레이아웃 방향이 승인되기 전에 픽셀 단위의 상세 디자인을 만드는 데 토큰과 시간을 사용하지 않습니다. 사용 가능한 도구로 이미지를 만들 수 없으면 가장 작은 유용한 와이어프레임 또는 주석이 있는 기존 화면을 제시하고 제한사항을 기록합니다.
- 기존 UI를 확장하기 전에 먼저 발견해야 할 디자인 시스템으로 취급합니다. 의미가 호환되는 동안 기존 컨트롤 클래스, 래퍼, 리소스 방식, 명명 규칙, 이벤트/메시지 흐름, 레이아웃 헬퍼, 테마 값, 아이콘, 검증·오류 처리를 재사용합니다. 새 컴포넌트가 꼭 필요하면 기존 컴포넌트군과 모양·동작을 맞추고 재사용이 부족했던 이유를 기록합니다.
- 의존성은 재사용 우선으로 판단합니다. 새 유틸리티, 컨트롤, 리소스, 의존성을 만들기 전에 저장소, 프로젝트 파일, 패키지 매니페스트, 리소스 디렉터리, 빌드 설정에서 기존 구현 또는 이미 참조된 라이브러리를 검색합니다. 호환되는 기존 항목을 적응해 사용하는 것을 우선하며, 시각 효과 하나만을 위해 라이브러리를 추가하지 않습니다. 새 의존성 또는 교체가 필요하면 목적, 호환성·라이선스·빌드 영향, 검토한 대안, 중요한 경우 PM/사용자 승인 여부를 기록합니다.
- 개발자는 가능한 한 프로젝트의 기존 UI 제작 방식을 통해 GUI 디자인을 구현합니다. 같은 다이얼로그/뷰/컨트롤 생성 경로, 리소스 또는 마크업 규칙, 이벤트/메시지 연결, 상태 관리, 스타일 확장 지점을 사용합니다. 근거와 시스템 설계자 확인 없이 병렬 UI 아키텍처를 만들거나 프레임워크를 혼합하지 않습니다.
- 로직 규모가 큰 변경은 Sample Code 우선 루틴을 사용합니다. 가장 작은 동작 또는 인터페이스 단위를 분리하고 프로젝트 고유 방식의 최소 Sample Code 또는 집중 단위 테스트·특성화 테스트를 작성한 뒤, 대표적인 성공·실패 입력으로 실행하고 결과를 기록합니다. Sample Code가 통과한 후에만 더 넓은 코드 경로로 확장하며, 검증된 단위 하나씩 통합합니다. Sample Code가 실패하면 대규모 수정을 진행하기 전에 접근 방식을 보완하고 다시 실행합니다.
- GUI QC는 모던한 시각 품질과 기존 제품과의 연속성을 함께 확인합니다. 대상 화면을 기준 화면·참조 화면과 비교하고 일반·호버·포커스·비활성·로딩·빈 상태·오류 상태, 해당되는 경우 키보드·접근성 동작을 검증합니다. 재사용된 컴포넌트가 기존 의미를 유지하는지도 확인하며, 스크린샷 또는 재현 절차로 시각 차이를 기록하고 승인된 의도적 변경과 회귀를 구분합니다.
- 필수 조사와 검증을 생략하지 않는 범위에서 컨텍스트와 토큰 사용량을 최적화합니다. 먼저 파일명, 심볼, 프로젝트 매니페스트, 리소스 목록, 대상 검색 결과를 확인하고 후보 파일의 관련 구간만 읽은 뒤 근거가 있을 때 범위를 넓힙니다. 변경되지 않은 같은 파일이나 로드맵·인수인계·QC 근거를 반복해서 주입하거나 다시 서술하지 않습니다. 공유 산출물은 결정, 참조 위치, 변경 내용, 위험, 다음 작업 중심의 짧고 구조화된 형식으로 유지하고, 내용을 복사하는 대신 안정적인 프로젝트 파일을 참조합니다. 각 에이전트에는 맡은 작업에 필요한 발췌 내용과 제약만 전달하고, 작업 완료 시 요약을 만들어 다음 단계에서 재사용합니다. 안전한 독립 조사·검증은 병렬로 처리하되 공유 파일 편집과 아키텍처 결정은 순차적으로 진행합니다.
- GUI 및 소프트웨어 작업은 아키텍처, 명명 규칙, 서식, 제어 흐름, 오류 처리, 프로젝트 기본 도구를 포함한 기존 프로젝트 관례와 최대한 일치시킵니다. 차이가 필요한 경우 기술적 이유를 기록하고 시스템 설계자의 확인을 받습니다.
- 근거 없이 변수를 추가하지 않습니다. 새 변수를 만들기 전에 같은 목적에 안전하게 사용할 수 있는 기존 값을 검색하고, 범위·수명·의미가 호환되면 이름이 달라도 재사용합니다. 단, 의미를 불분명하게 만들거나 안전하지 않은 결합을 초래하는 재사용은 하지 않습니다.
- 적합한 승인 스킬이 없으면 시스템 설계자는 부족한 역량을 보고하고 PM에게 스킬 또는 스킬 생성 작업을 제안합니다. 스킬 설치, 외부 서비스 연결, 중요한 의존성 도입 전에는 PM/사용자 승인을 받습니다.
- QC가 스킬 제약 준수 여부를 확인할 수 있도록, 대상 역할과 목적을 포함한 스킬 배정을 로드맵에 기록합니다.
- 승인된 GUI 인수인계를 화면과 상호작용의 기준 문서로 취급합니다. 사용자 흐름, 레이아웃, 컴포넌트 동작, 접근성에 영향을 주는 변경은 GUI 디자이너 검토가 필요하며 범위가 변경되면 PM 승인도 받습니다.
- 사용자 GUI 검토 피드백과 확인 결과를 디자인 인수인계 자료와 함께 보관합니다. 중요한 사용자 결정이 미해결 상태이면 사용자 또는 PM이 방향을 정할 때까지 해당 GUI 단계를 진행하지 않습니다.
- C++과 C#에서는 프로젝트에 이미 있는 빌드·테스트 명령을 우선 사용합니다. 사용자 승인 없이 새 빌드 시스템이나 의존성을 도입하지 않습니다.
- 외부 라이브러리·SDK·API 연동은 다음 Debug 루틴을 따릅니다. (1) 버전, 필수 설정, 자격 증명·엔드포인트 전제, 프로젝트 고유 빌드 대상을 기록합니다. (2) 프로젝트의 Debug 구성으로 빌드하여 의존성 로드·링크를 확인합니다. (3) 디버그 심볼과 필요한 로그를 켜고 실제 프로그램 또는 프로젝트 내부의 최소 스모크 경로를 실행합니다. (4) 해당되는 경우 초기화, 주요 호출, 반환 데이터·상태 변경, 콜백·이벤트 흐름, 타임아웃·취소, 오류 처리, 정리·해제를 실행합니다. (5) 예외, 어설션, 반환 코드, 로그, 스레드·UI 스레드 규칙, 리소스 소유권, 종료 동작을 확인합니다. (6) 외부 상태에 의존하는 연동이면 잘못된 설정 또는 서비스 불가 경로를 최소 한 가지 검증합니다. (7) 재현 절차, 환경, 기대 결과와 실제 결과, 증거를 기록합니다. Debug에서 실제 구동 성공을 확인하기 전에는 연동을 완료 처리하지 않으며, 해결되지 않은 실패는 차단 요소로 보고하거나 남은 위험을 포함한 PM/사용자 예외 승인을 기록합니다.
- QC는 검증된 결함과 제안을 구분해야 합니다. 출시 차단 결함에는 근거, 기대 결과와 실제 결과, 명확한 담당자가 필요합니다.
- QC 실패 항목은 QC가 통과 재검증을 기록하거나 PM/사용자가 남은 위험을 포함한 예외를 문서로 승인하기 전까지 완료로 처리하지 않습니다.
- 사용자가 다른 언어를 요청하지 않는 한, 로드맵 요약, 작업 플랜, GUI 검토 기록, QC 결과, 진행 보고, 최종 결과는 한글로 출력합니다. 소스 코드, 명령어, 경로, API 이름, 그 밖의 식별자는 변경하지 않고 필요할 때 한글로 설명합니다.
- 필요한 결정, 자격 증명, 외부 서비스, 완료 기준을 확보할 수 없으면 시스템 설계자/PM 또는 사용자에게 계속 진행하기 위해 필요한 최소한의 결정을 보고합니다.
