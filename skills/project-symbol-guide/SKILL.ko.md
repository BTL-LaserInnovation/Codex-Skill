# 프로젝트 심볼 가이드

프로젝트가 이미 제공하는 기능을 다시 찾아 사용할 수 있도록 정리합니다. 분석 결과는 대상 프로젝트에 저장하여 이후 세션에서도 검색·검증·재사용합니다. “머지프로젝트”는 프로젝트 병합을 연상시키므로, 분석 목적을 드러내는 **프로젝트 심볼 가이드**를 표시 이름으로 사용합니다.

## 범위와 참조 저장

사용자 요청과 작업 디렉터리에서 대상 프로젝트를 확인하고 적용 지침, 빌드 설정, 기존 분석 자료를 읽습니다. 구조도가 있으면 관련 모듈을 좁히는 데 활용합니다. 다른 스킬이나 특정 언어·도구 설치를 필수로 요구하지 않습니다.

프로젝트에 기존 저장 위치가 없다면 다음 위치를 사용합니다.

```text
docs/project-analysis/
  index.json           # 분석 범위, 소스 지문, 소유자, 심볼 검색
  classes/<owner>.md   # 클래스별 변수·함수와 근거
  modules/<owner>.md   # 자유 함수, 전역 변수, 모듈 심볼
```

자료 생성·갱신 시 [목록 형식](references/catalog-format.ko.md)을 읽습니다. 프로젝트별 분석은 설치된 스킬 내부에 저장하지 않습니다. 소스 본문이나 비밀값을 목록에 복사하지 않습니다.

최초 전체 분석은 자체 소스 파일과 빌드 구성을 열거한 뒤 해당 범위의 클래스와 모듈 심볼을 분석합니다. 특정 작업 요청에서는 영향받는 모듈부터 시작할 수 있습니다. 완료·미분석·제외 파일과 파서·빌드 구성의 한계를 명시합니다. 발견한 후보를 모두 정리했어도 미분석 파일이 있으면 부분 분석입니다. 이름만 뽑은 정규식 검색을 의미 분석으로 표시하지 않습니다.

## 클래스·변수·함수 분석

사용 가능한 컴파일러·언어 서버·AST 정보로 심볼을 해석합니다. 없으면 범위를 좁힌 `rg` 검색과 직접 소스 읽기를 사용하며, 불확실한 관계는 추측하지 않고 표시합니다. 선언·구현·관련 사용처를 함께 확인하고 분할/partial 클래스, 상속, 오버로드, 템플릿/제네릭, 조건부 컴파일을 반영합니다.

클래스마다 한정 이름, 책임, 기반 클래스/인터페이스, 소스 위치, 관련 모듈을 기록합니다. 직접 선언한 멤버와 상속받은 멤버를 구분하고 원래 선언 클래스로 연결합니다.

동작 이해나 구현에 필요한 변수·프로퍼티·필드는 다음을 기록합니다.

- 소유자와 한정 이름, 자료형, 접근 범위, 인스턴스/static/상수 구분, 선언 위치.
- 용도, 안전하게 기록할 수 있는 초기값/기본값, 유효 범위·단위, 근거가 확인된 수명·소유권·스레드 조건.
- 확인된 읽기/쓰기 함수와 근거. 직접 쓰기와 간접 변경 또는 해석하지 못한 변경을 구분합니다.

분석 범위 내 클래스의 선언된 멤버 변수는 모두 목록화합니다. 매개변수·지역 변수는 동작, 상태 전이, 재사용에 중요한 경우 소속 함수 아래에 기록하고 이 수집 기준을 목록에 명시합니다. 관련 전역/모듈 변수는 모듈에 정리합니다.

함수·메서드는 다음을 기록합니다.

- 한정 이름과 전체 서명, 접근 범위, 해당 언어의 static/virtual/async 등의 속성, 선언·구현 위치.
- 용도, 입력, 출력, 오류 처리, 사전 조건, 상태 변경, 부수 효과, 근거가 확인된 소유권·스레드 제약.
- 확인된 호출자/피호출자, 읽고 쓰는 변수와 소스 근거. 해석되지 않은 관계는 명시합니다.
- 재사용 조건, 확인 가능한 기존 호출 예와 테스트. 선언만 있거나 외부에 있는 함수와 구현까지 확인한 함수를 구분합니다.

범위 내 클래스/모듈의 선언된 함수는 생성자, 소멸자, 접근자, 오버로드까지 모두 목록화하되 행동 설명의 깊이는 중요도에 맞춥니다. 관계 목록이 비어 있으면 “이 범위에서 관찰되지 않음”을 뜻하며 관계가 없다는 증명으로 취급하지 않습니다. 동적 호출, 리플렉션, 이벤트, 매크로, 별칭, 함수 포인터는 미해결 항목이 될 수 있습니다.

## 추천 전 최신성 확인

스킬을 실행할 때 기존 색인부터 읽습니다. 기록된 소스 파일 목록과 내용 지문을 현재 파일과 비교하며 커밋되지 않은 변경과 관련 미추적 소스도 포함합니다. Git 커밋이 같다는 사실만으로 최신이라고 판단하지 않습니다. 비교가 불가능하면 현재 판단에 사용할 소스를 다시 읽고 나머지 범위의 한계를 보고합니다.

변경·추가·삭제·이름 변경 파일과 관련 소유자 및 양방향 참조를 갱신합니다. 서명, 자료형, 상속, 상태 계약이 바뀌면 의존 항목도 다시 확인합니다. 사라진 검색 항목과 끊어진 링크는 제거하고, 검증되어 유용한 경우에만 이름 변경 대응을 남깁니다. 영향 없는 기록과 프로젝트 작성 메모는 유지합니다. 편집 후 근거 위치를 갱신하며 관련 항목을 정합화하기 전에는 파일의 분석 완료 지문을 새 값으로 바꾸지 않습니다.

허가된 코드 변경과 관련 검증 후 목록을 갱신합니다. 분석 상태와 빌드/검증 상태를 분리합니다. 빌드에 실패했어도 목록은 현재 소스와 일치할 수 있습니다. 갱신은 스킬 실행 중 수행하며, 세션 사이에 백그라운드 감시나 자동 동기화가 이루어진다고 안내하지 않습니다.

## 현재 작업에 필요한 심볼 추천

요청 동작을 책임, 상태, 입력, 출력으로 나눕니다. 목적·별칭·자료형·소유자·서명·사용처로 목록을 검색하고 유력 후보의 현재 소스와 직접 계약을 확인합니다. 초기 범위에 적합한 후보가 없으면 관련 모듈, 기반 클래스, 모듈 심볼, 사용 가능한 기존 의존성/라이브러리까지 확장합니다.

실제로 필요한 최소한의 변수·함수를 추천합니다. 후보마다 고정 ID, 한정 이름/서명, 클릭 가능한 소스 위치, 적합한 이유, 접근·수명·스레드·의존성 제약을 제시합니다. 변수와 함수가 함께 재사용 경로를 이루면 연결 방법을 설명합니다. 이름 유사성보다 동작 적합성과 호환성으로 우선순위를 정합니다. 접근 불가·호환 불가 후보는 짧게 이유를 남깁니다. private 멤버 재사용을 위해 캡슐화를 약화하거나 저장 상태를 중복하지 않습니다.

적합한 심볼이 없으면 검색 범위·검색어, 관련 탈락 후보, 남은 불확실성을 보고합니다. 의존성에 접근하지 못하거나 파서가 해석하지 못한 결과는 검색 한계이지 심볼이 없다는 증거가 아닙니다.

## 없는 심볼 보완과 새 함수 허가

분석·추천 요청은 목록 갱신을 허용하며 프로젝트 구현까지 허용하지는 않습니다. 분석만 요청받았다면 부족한 심볼을 제안으로 남깁니다. 구현이 요청된 경우 재사용 검색 후 필요한 새 변수를 프로젝트의 소유자·자료형·초기화·수명·접근 규칙에 맞춰 추가합니다. 허가된 구현 범위 내 변수 생성에는 별도 허가를 요구하지 않습니다. 사용하지 않는 예상 상태는 추가하지 않습니다.

**새 프로젝트 함수는 선언이나 본문을 프로젝트 소스에 쓰기 전에 사용자 허가가 필요합니다.** 메서드, 보조 함수, 지역 함수, 새 오버로드, 생성자/소멸자, 접근자, 콜백/람다, 함수를 포함한 생성 코드도 해당합니다. 보조 함수 이름 변경이나 생성 작업 위임으로 우회하지 않습니다. 기존 함수 내부 수정은 허가된 구현 범위를 따르며 공개 계약을 실질적으로 교체하면 승인 대상으로 제시합니다.

질문하기 전에 검색을 완료하고 다음을 구체적으로 준비합니다.

- 기존 변수·함수로 해결할 수 없는 이유와 검색 근거.
- 소유자, 대상 파일, 전체 서명, 목적, 입력/출력, 부수 효과, 예정 호출자.
- 필요한 변수·의존성, 검증 계획, 이번 허가로 생성할 정확한 함수 목록.

해당 함수들의 생성을 명시적으로 허가받고, 이 스킬에 기록된 사용자의 함수 생성 규칙 때문임을 설명하며 이 `SKILL.md`에 링크합니다. 대화에서 서명을 제안할 수 있지만 허가 대기 중에는 프로젝트 파일에 함수 틀이나 본문을 쓰지 않습니다. 독립적인 분석·목록 정리는 계속합니다. 무응답은 허가가 아닙니다. 식별된 함수 생성을 명시한 기존 지시나 제안 함수 집합에 대한 이전 승인이 있으면 유효하며, 포괄적인 기능 요청만으로는 충분하지 않습니다. 승인 범위나 계약이 실질적으로 확대될 때만 다시 묻습니다. 승인 후 구현·검증하고 함수와 변수 참조를 함께 갱신합니다. 변수 변경에 새 생성자·접근자·보조 함수가 필요하면 그 함수 허가 전에 종속 편집을 하지 않습니다.

## 결과 보고

목록 위치, 분석 범위·최신성·중요한 누락, 현재 작업의 후보 또는 부족한 심볼 제안을 제시합니다. 기존 심볼, 승인된 변경, 제안을 구분합니다. 코드 변경 시 검증 결과를 요약하고 변수/함수 관계 양쪽을 갱신합니다. 부분 분석을 프로젝트 전체 분석으로 보고하지 않습니다.
