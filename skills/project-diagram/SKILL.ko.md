# 프로젝트 다이어그램

소프트웨어 프로젝트의 구조를 만들거나 갱신·검토·시각화할 때 이 스킬을 사용합니다. 이후 작업에서 전체 코드를 반복해서 읽는 대신, 신뢰할 수 있는 압축 아키텍처 지도로 변경 범위를 먼저 파악하는 것이 목적입니다.

## 다이어그램 산출물

프로젝트 루트 아래에 다음 정식 산출물을 유지합니다.

```text
docs/architecture/
├─ project-diagram.mmd        # 사람이 읽는 Mermaid 원본이자 렌더링 기준
└─ project-diagram.index.json # 구성 요소·관계·소스 매핑용 기계 판독 인덱스
```

기존 저장소에 문서 위치 규칙이 있으면 그 위치를 보존합니다. 생성 이미지를 원본으로 삼지 않습니다. Mermaid 파일과 JSON 인덱스에는 생성/갱신 시각을 기록하고, 각 구성 요소를 관련 파일 및 안정적인 심볼에 연결하며 서로 일치시킵니다. 두 파일을 새로 만들거나 크게 고칠 때는 [산출물 형식](references/artifact-format.ko.md)을 읽습니다.

최초 프로젝트 구성 후와 아키텍처 변경, 프로젝트·모듈 추가/제거, 공개 인터페이스 변경, 의존성 변경, 의미 있는 UI·데이터 흐름 변경 후에 산출물을 만들거나 갱신합니다. 솔루션, 매니페스트, 빌드 파일, 공개 인터페이스, 진입점, 대상 소스 조사를 근거로 관계를 기록합니다. 파일명만으로 관계를 추정하지 않습니다.

## 다이어그램 우선 변경 절차

코드를 계획하거나 편집하기 전에 다음을 수행합니다.

1. 다이어그램과 JSON 인덱스를 찾아 읽고, 영향 구성 요소 ID·인접 요소·의존 방향·진입점·테스트·매핑된 파일을 확인합니다.
2. 산출물이 요청 범위를 포함하는지, 최근 변경으로 오래되지 않았는지 확인합니다. 오래되었다면 매니페스트, diff, 영향 파일만 조사하여 해당 영역을 갱신합니다. 오래된 다이어그램을 사실의 증거로 취급하지 않습니다.
3. 영향 하위 그래프를 기반으로 구현 계획을 세운 뒤, 실제 대상 코드와 직접 계약을 읽고 수정합니다. 다이어그램은 조사 범위를 줄이는 도구이며 소스 수준 검증을 대체하지 않습니다.
4. 변경 및 검증 후 영향 노드·엣지·파일/심볼 매핑·관련 흐름·시각·변경 메모를 갱신합니다. 모순되는 이력이 남지 않도록 오래된 매핑을 제거합니다.

조사 범위는 비례하게 유지합니다. 최초 전체 지도에는 폭넓은 분석이 필요할 수 있습니다. 이후에는 인덱스의 하위 그래프에서 시작하고, 엣지·계약·빌드 결과·테스트가 더 넓은 영향을 보여 줄 때만 확장합니다.

## 시각화 요청

사용자가 다이어그램을 보기, 이미지화, 내보내기, 시각화해 달라고 요청하면 정식 Mermaid 원본을 결정론적 Mermaid 호환 렌더러로 변환합니다. 선명하고 검토 가능한 SVG를 우선하며, 사용자가 요청하거나 전달 환경에서 필요할 때만 PNG도 생성합니다. 프로젝트에 생성 산출물 위치 규칙이 없다면 `docs/architecture/generated/`에 저장하고 출력 경로를 알립니다.

생성형 이미지 모델로 기술 아키텍처 다이어그램을 다시 그리지 않습니다. 레이블·관계·위상을 바꿀 수 있기 때문입니다. 호환 렌더러가 없으면 Mermaid 원본을 제공하고 렌더링 제한을 알리며, 임의의 이미지를 만들지 않습니다.

## 다이어그램 품질

구현 판단에 도움이 되는 정보만 모델링합니다. 즉 배포 단위 프로젝트/앱, 모듈, 공유 라이브러리, 데이터 저장소, 외부 시스템, UI 경계, 핵심 데이터·제어 흐름, 그리고 구성 요소를 제약하는 테스트를 기록합니다. 의존성에 영향을 주지 않는 구현 상세 노드는 접습니다. 안정적인 ID, 방향과 레이블이 있는 엣지, 간단한 범례를 사용합니다. 두 산출물 모두에 비밀값, 민감한 값, 무관한 내부 상세를 기록하지 않습니다.
